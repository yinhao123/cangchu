## 1. 对标基准

### 1.1 对标的是哪一档产品

不是金蝶 / 用友 / 唯智那类项目制 WMS，而是**年费几百到几千、卖给中小仓库的标准化基础版**。这一档的功能清单高度收敛：

| 模块 | 商用基础版的标准配置 |
|---|---|
| 基础档案 | 商品（SKU/规格/分类/条码/单位/参考价）、仓库、往来单位、**Excel 批量导入导出** |
| 出入库 | 扫码入库 / 出库、单据审核、**各类单据打印**（采购单、入库单、领用单、调拨单） |
| 盘点 | **盘点单生成 → 盘点录入 → 差异比对 → 审核调整**（明盘 / 抽盘 / 循环盘点） |
| 调拨 | 同仓移位、跨仓调拨、调拨单 |
| 单据 | 采购订单、销售订单、领用申请（申请-审批-执行） |
| 报表 | 出入库流水、库存总表（含金额）、采购/销售统计、**多维导出** |
| 权限 | 管理员 / 仓管员 / 只读，按仓库分权 |
| 增值项（另收费） | 批次效期、序列号追溯、应收应付、多账套、生产工单 |

### 1.2 我们已经强于对方的地方（不要为凑功能稀释掉）

| 能力 | 本项目 | 商用基础版普遍情况 |
|---|---|---|
| 账本不可变 | `trg_logs_no_delete` + `trg_logs_immutable`，任何代码路径都改不了历史 | 多数允许直接改库或"反审核即改"，审计对不上 |
| 幂等 | `stock_logs.client_msg_id UNIQUE` + 单据派生 `bill_msg_id` | 大量产品重复点击就双倍扣账 |
| 并发安全 | 条件更新 + `rowcount` 判定，实测 8 线程零负库存 | 先查后写，弱网/多端下出负库存 |
| 单据原子性 | `post_bill_lines()` 整单回滚，不留半截 | 常见"单据审了、库存没加" |
| 溯源 | 每条流水带 `ref_type` + `ref_id`，双向可追 | 单据与流水脱节 |
| 离线续传 | 客户端 `client_msg_id` + 批量 SAVEPOINT 错误隔离 | 部分支持 |

**这份清单是本项目的销售话术底牌**，补功能时不得引入"直接改账"的捷径（例如为导入方便而 `UPDATE stock_current`，或为盘点方便而 `UPDATE stock_logs`）。

### 1.3 差距矩阵

| 商用基线功能 | 本项目现状 | 差距性质 |
|---|---|---|
| Excel / CSV 批量导入导出 | ❌ `api/products.py` 只有单条 CRUD，无任何导入通路 | **缺通路**（P0-1） |
| 盘点单工作流 | ❌ 只有单条 `ADJUST`，且代码明确「盘点调整单不可冲销」 | **缺工作流**（P0-2） |
| 单据打印 | ❌ `Labels.tsx` 是唯一有 `@media print` 的页面，只打标签 | **缺输出**（P0-3） |
| 销售订单 / 销货单 / 退货 / 客户对账 | ❌ `partners.type` 有 `CUSTOMER`，但没有销货单，出库只能逐条扫 | **缺闭环**（P1-4） |
| 库存金额 / 成本 | ⚠️ `stock_logs.unit_price/amount` 只在入库侧有值，出库不带成本 | **缺口径**（P1-5） |
| 按仓库分权 | ❌ 只有 `admin` / `operator` 两级，operator 可见全部仓库与成本价 | **缺维度**（P1-6） |
| 操作审计日志 | ❌ 无 `audit_logs` 表，只有库存流水 | **缺留痕**（P1-6） |
| 采购订单 / 采购入库 | ✅ `wms_purchase_order` + 审批过账 | 无差距 |
| 领用 / 退库 / 归还 / 借用 / 调拨 | ✅ `wms_goods_operation_order`（五种 op_type） | 无差距 |
| 仓库 / 库位两级 | ✅ `warehouses.parent_id` + `level` | 无差距 |
| 条码 / 标签打印 | ✅ Code128 SVG/PNG + `@media print` 标签网格 | 无差距 |
| 流水 / 库存 / 汇总 / CSV | ✅ 已实现 | 部分差距（无金额列，见 P1-5） |
| 库存预警 | ⚠️ `min_stock` 有字段、仪表盘有低库存提示，无主动推送 | 可延后（P2-B） |
| 批次 / 效期 / 序列号 | ❌ schema 无 batch / expiry 维度 | P2-A |

## 2. 范围与优先级判定

### 2.1 判定标准（三条，按顺序）

1. **客户第一周会不会撞上**：撞上就退单的，进 P0。
2. **后补是否要改账本表结构**：要改 `stock_logs` / `stock_current` 的维度（批次、序列号、多单位），必须在第一次交付前想清楚做不做，不能等。
3. **是否是销售承诺项**：报价单上写了却做不出来的，等于违约。

只有第 1 条为"是"的进 P0；只有第 2 条为"是"的进 P2-A 并**必须在售前问清客户类型**；第 3 条按实际报价内容决定。

### 2.2 P0 / P1 / P2 定义

| 级别 | 含义 | 处理方式 |
|---|---|---|
| P0 | 缺了就无法交付给真实客户 | 本轮必做，做完才发版 |
| P1 | 客户用满一个月必然提出 | 按客户类型选做，售前确认 |
| P2 | 有客户提再做，但设计上要留口 | 只登记，不排期 |

### 2.3 明确不做（承接 `docs/13` 第 3 章，新增理由）

| 不做项 | 理由 |
|---|---|
| Excel `.xlsx` 直接读写 | 需引入 `openpyxl`，违反「不得引入 PRD 2.1 未列出的依赖」。提供 CSV 模板 + 「Excel 另存为 CSV」引导文案，是约束下的正确取舍 |
| Flowable / BPM | 单级审批已够；`docs/13` 决策 2 已定 |
| 多租户 / 货主隔离 | 局域网单机自用，无租户概念 |
| 波次拣货 / 复核称重 / 电子面单 | 小仓库单量用不上，且强依赖 PDA 与快递接口 |
| 应收应付凭证 / 开票 | 与财务系统边界，不属于仓库职责；P1-4 只做到「对账单」为止 |
| 资产台账 / 折旧 | `docs/13` 决策 4 已砍，仅留 `is_join_asset` 标记 |
| 多账套 | 单机单账本，多账套等于多份数据库文件，安装包里放两个 exe 即可，无需功能化 |

## 3. P0-1 · 基础数据批量导入 / 导出

### 3.1 问题

`api/products.py` 只有 `list / create / update / delete / restore` 五个单条接口，没有任何导入通路。真实上线的第一个动作是「把客户现有的商品档案和期初库存搬进来」：

- 商品 800~3000 条，手输等于 3~5 人日，且必错。
- **期初库存没有任何合法入口**。只能造「入库单」刷进去，这会让采购统计、供应商对账、单据 CSV 导出全部失真；而账本不可删不可改，错了只能逐条冲销——上线第一天就制造一堆脏数据。
- 反向也缺：客户会要求「把商品列表导出成 Excel 给我核对」，现在只能一页 20 条翻页。

### 3.2 方案

**两段式无状态导入**（不引入临时表、不引入会话状态）：

```
用户上传 CSV ──▶ POST /api/imports/preview (dry_run=true)
                      │
                      ├─ 有错 → 返回逐行错误清单（前端表格展示，可下载错误报告）
                      │
                      └─ 无错 / 用户选择"仅导入通过行" → POST /api/imports/commit
                                                                    │
                                                                    └─ 单事务落库
```

- `preview` 与 `commit` **共用同一个解析与校验函数**，避免"预检通过、提交失败"的经典分歧。
- 提交采用 `skip_invalid` 开关：`false` 时整批回滚（默认）；`true` 时逐行 `SAVEPOINT` 隔离（T-08），成功的留、失败的报。
- **幂等**：期初库存的行幂等键由 `barcode + warehouse_code` 确定性派生（复用 `bill_no_service.bill_msg_id` 的做法），重复上传同一文件不会重复加库存。这是本功能唯一的高风险点。

### 3.3 支持的三类导入

| kind | 目标表 | 必填列 | 特殊规则 |
|---|---|---|---|
| `products` | `products` | `name` | `barcode` 可空；`unit` 默认「件」；`cost_price`/`sale_price` 缺省 0；`min_stock` 缺省 0；重名 + 重条码按冲突处理 |
| `partners` | `partners` | `name`, `type` | `type` ∈ `CUSTOMER`/`SUPPLIER`（大小写不敏感，入库统一转大写）；`(name,type)` 冲突 |
| `opening-stock` | `stock_logs` + `stock_current` | `barcode`, `warehouse_code`, `qty` | `qty` 必须 > 0；必须**先**有商品与仓库；走 `stock_service` 入库入口，`ref_type='OPENING'`，`remark='期初建账'` |

### 3.4 文件格式约定

| 项 | 规定 |
|---|---|
| 编码 | 先按 `utf-8-sig` 解码，失败回退 `gbk`；两者都失败 → `422 {code:1019}` 提示「请另存为 UTF-8 或 GBK 编码的 CSV」 |
| 分隔符 | 逗号；字段含逗号/引号时按 RFC 4180 双引号转义（用标准库 `csv`） |
| 表头 | 必须是模板第一行，按名称匹配（顺序无关）；缺列 → `422 {code:1019}` 并列出缺失列名 |
| 行数 | 单次 ≤ 5000 行、文件 ≤ 5 MB，超限 → `422 {code:1020}` |
| 空行 | 全空行跳过，不计入错误 |
| 数值 | 去空白；`¥`、`,`、空格自动剥离；`qty` 必须是整数，小数 → 该行失败 |

### 3.5 接口

| 方法 | 路径 | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/imports/templates/<kind>` | 已登录 | 下载 CSV 模板（含表头 + 2 行示例 + 注释行），`utf-8-sig` + `\r\n`（T-10） |
| POST | `/api/imports/preview` | 已登录 | `multipart/form-data`：`kind` + `file`；返回统计与逐行错误，**不落库** |
| POST | `/api/imports/commit` | 已登录 | 同上 + `skip_invalid`（默认 `false`）；`opening-stock` 仅 `admin` |
| GET | `/api/imports/export/<kind>` | 已登录 | 商品 / 往来单位 / 当前库存导出 CSV（当前库存导出必须含 `qty` 与 `avg_cost`） |

响应示例（`preview`）：

```json
{
  "code": 0, "msg": "ok",
  "data": {
    "kind": "products",
    "total": 812, "valid": 806, "invalid": 6,
    "errors": [
      {"row": 12, "field": "barcode", "value": "6901234567890", "msg": "条码已被「可乐 330ml」占用"},
      {"row": 47, "field": "name", "value": "", "msg": "不能为空"}
    ],
    "preview": [{"row": 2, "name": "矿泉水 550ml", "barcode": "6900000000001", "ok": true}]
  }
}
```

### 3.6 期初建账的硬约束（★ 最容易做错的一处）

1. **必须走 `stock_service` 的入库入口**，不得直接 `INSERT stock_current`（铁律：账本唯一入口）。
2. **只在「账本为空」时允许**：`SELECT COUNT(*) FROM stock_logs` 不为 0 → `409 {code:1021}`，
   提示「本账本已有流水，期初建账只能在新库执行；如需修正请用盘点单」。
3. **幂等键确定性派生**：`bill_msg_id('OPENING', hash(barcode + warehouse_code))`，
   同一文件重复提交返回 `duplicated:true`，不重复加库存。
4. **不挂 `partner_id`**、`source='WEB'`、`ref_type='OPENING'`，且**不参与**采购统计与供应商对账
   （所有按 `ref_type` 聚合的报表都要排除 `OPENING`，或者单列一项「期初」）。
5. `avg_cost` 取 `products.cost_price`（期初没有实际采购价）。

### 3.7 落位

| 层 | 文件 | 内容 |
|---|---|---|
| api | `api/imports.py`（新） | 4 个路由，薄层，只做取参与包络 |
| services | `services/import_service.py`（新） | 解析、编码探测、逐行校验、dry_run/commit 共用逻辑 |
| services | `services/import_service.py: TEMPLATES` | 三类模板的列定义（单一真相，表头/校验/错误提示都从这里来） |
| models | `models/import_repo.py`（新） | 批量 INSERT（`executemany`）+ 冲突检测查询 |
| 前端 | `pages/ImportExport.tsx`（新） | 上传 → 预检结果表格（错误行高亮）→ 确认导入；模板下载按钮 |
| 前端 | `layout/nav.ts` | 「基础资料」组下新增「批量导入」；「库存报表」组导出按钮复用 |

> 不在 `products.py` 里加导入接口：`products.py` 是单条 CRUD 的薄层，混入 multipart 解析会破坏它的定位。

### 3.8 异常处理

| 场景 | 处理 |
|---|---|
| 文件为空 / 只有表头 | `422 {code:1019}`「文件没有数据行」 |
| 编码无法识别（乱码） | `422 {code:1019}`，提示另存为 UTF-8/GBK |
| 表头缺列 / 多出未知列 | 缺列 422；未知列忽略但响应里列出（防止用户以为导入了） |
| 条码冲突 | 该行失败，`data.errors` 回传冲突商品的 `id/name`（与 `docs/03` 商品创建冲突口径一致） |
| `opening-stock` 引用了不存在的条码 | 该行失败，`1019` +「条码未登记」，提示先导商品 |
| 提交时并发写冲突 | `BEGIN IMMEDIATE` 串行化，冲突由 `busy_timeout=5000` 吸收；超时 → `503 {code:1012}` |
| 中途断电 | 单事务，全量回滚，不留半截（`skip_invalid=false` 时） |

- [ ] 800 行商品 CSV（含 6 行故意错误）→ preview 精确报出 6 行 + 行号 + 字段

## 4. P0-2 · 盘点单

### 4.1 问题

当前只有 `stock_service.adjust()`：一次一条商品、一个仓库、一个目标值，且 `remark` 必填、仅 `admin`、**不可冲销**。真实盘点是这样：

```
仓管拿着打印的空白盘点表，在货架间走一圈填实数
  → 回来录入系统（可能几十上百行，其中大部分无差异）
  → 主管看差异、问原因
  → 一次性过账
```

用现接口做一件真实盘点，等于让仓管在系统里点一百次「盘点调整」，且没有"这次盘点是几号单、盘了哪些、差异多少"的凭据。**这不是效率问题，是功能缺失。**

### 4.2 方案：盘点单作为第四类单据

```
DRAFT ──生成快照──▶ DRAFT(已快照) ──提交──▶ SUBMITTED ──admin 审批──▶ POSTED
  │                                            │
  │                                            └──驳回──▶ REJECTED ──改──▶ SUBMITTED
  └──作废──▶ CANCELED（未过账才可作废）
```

- 建单即生成明细快照：`INSERT INTO wms_stocktake_detail SELECT ... FROM stock_current`。
- **只快照 `qty != 0` 的行**；空库位盘出实物（盘盈新发现）通过「手工追加行」处理。
- 支持按仓库 + 可选分类 / 库位筛选生成，避免每次全盘。
- 过账**复用 `stock_service.post_bill_lines()`**，`ref_type='STOCKTAKE'`，绝不自己写 `stock_current`。

### 4.3 ★ 设计决策：过账数量用「实时当前值」，不是快照差

这是本功能唯一的实质难点，必须先定口径再写代码。

盘点期间若仓库仍有人出库（现实里几乎必然发生），`book_qty`（建单快照）会过时：

| 口径 | 公式 | 结果 |
|---|---|---|
| A. 快照差 | `quantity = real_qty - book_qty` | 期间出的货会被"加回来"→ 账又错了 |
| B. 实时差 | `quantity = real_qty - 实时当前值` | 账一定等于实盘数，但覆盖了期间发生的事 |

**采用 B**，理由：`ADJUST` 的定义本来就是「`quantity` = 目标值 − 当前值」（`.codebuddy/rules/10-inventory-rules.md` 第 4 节），B 严格符合定义；A 会让库存对不上实物，与盘点目的相悖。

配套要求（缺一不可）：

1. 流水 `remark` 写明「盘点实盘 X（盘面 Y，期间变动 Z）」，让人看得懂这条调整为什么是这个数。
2. 差异**报表**仍按 `book_qty` 口径统计（管理上要看"账实差异"），与过账数量分离，两个数字各有用途。
3. 前端过账前若检测到该仓库在建单后有过流水，给出黄色提示「盘点期间有 N 笔出入库，已按实盘数调整」，**不阻断**。

### 4.4 DDL（`db/migrations/0005_wms_stocktake.sql`）

```sql
-- 盘点单：第四类单据（采购订单 PO / 采购入库 PI / 通用操作 GO / 盘点 ST）
CREATE TABLE IF NOT EXISTS wms_stocktake (
    id             INTEGER PRIMARY KEY AUTOINCREMENT,
    code           TEXT    NOT NULL UNIQUE,          -- ST + yyyymmdd + 4 位流水
    name           TEXT    NOT NULL CHECK (length(name) BETWEEN 1 AND 50),
    warehouse_id   INTEGER NOT NULL REFERENCES warehouses(id) ON DELETE RESTRICT,
    scope_category TEXT,                             -- 生成时的分类筛选（仅记录，不参与过账）
    status         TEXT    NOT NULL DEFAULT 'DRAFT'
                   CHECK (status IN ('DRAFT','SUBMITTED','REJECTED','POSTED','CANCELED')),
    book_locked_at TEXT    NOT NULL,                 -- 快照时刻（账面基准时间）
    posted_at      TEXT,                             -- 过账时刻
    operator_id    INTEGER NOT NULL REFERENCES users(id) ON DELETE RESTRICT,
    submitter_id   INTEGER REFERENCES users(id) ON DELETE SET NULL,
    approver_id    INTEGER REFERENCES users(id) ON DELETE SET NULL,
    remark         TEXT,
    created_at     TEXT    NOT NULL,
    updated_at     TEXT    NOT NULL,
    -- 状态与时间戳必须自洽，防止"已过账但没 posted_at"这类半截状态
    CHECK ((status = 'POSTED') = (posted_at IS NOT NULL))
);
CREATE INDEX IF NOT EXISTS idx_stocktake_status ON wms_stocktake(status, created_at DESC);
CREATE INDEX IF NOT EXISTS idx_stocktake_wh     ON wms_stocktake(warehouse_id, created_at DESC);

CREATE TABLE IF NOT EXISTS wms_stocktake_detail (
    id            INTEGER PRIMARY KEY AUTOINCREMENT,
    stocktake_id  INTEGER NOT NULL REFERENCES wms_stocktake(id) ON DELETE CASCADE,
    product_id    INTEGER NOT NULL REFERENCES products(id) ON DELETE RESTRICT,
    book_qty      INTEGER NOT NULL DEFAULT 0,        -- 快照账面数
    real_qty      INTEGER,                          -- 实盘数（NULL = 未盘，不参与过账）
    diff_qty      INTEGER NOT NULL DEFAULT 0,        -- real_qty - book_qty（录入时算好存下）
    product_name_snapshot TEXT NOT NULL,             -- 防改名（与 stock_logs 同口径）
    remark        TEXT,
    created_at    TEXT    NOT NULL,
    UNIQUE (stocktake_id, product_id),
    CHECK (real_qty IS NULL OR real_qty >= 0)
);
CREATE INDEX IF NOT EXISTS idx_stocktake_detail_st ON wms_stocktake_detail(stocktake_id);
```

> 明细不加 `warehouse_id`：整单一个仓库，冗余列会制造第二处真相。
> 需要同一次盘点跨仓，就开两张单。

### 4.5 过账映射

| 场景 | 流水 type | quantity | 说明 |
|---|---|---|---|
| `real_qty > 实时当前` | `ADJUST` | 差值（正） | 盘盈 |
| `real_qty < 实时当前` | `ADJUST` | 差值（负） | 盘亏 |
| `real_qty = 实时当前` | 不生成流水 | — | 无差异不落账，避免账本被无意义行灌满 |
| `real_qty IS NULL` | 跳过 | — | 未盘 |

- `client_msg_id = bill_msg_id(code, detail_id)`（确定性派生，重复审批幂等）。
- 过账后 `status='POSTED'`、`posted_at=now_iso()`。
- **已过账不可改、不可作废**。要更正：再开一张盘点单（与「ADJUST 不可冲销」的既有规则一致，
  见 `services/stock_service.py:reverse` 的 1014 分支文案「盘点调整单不可冲销，请再盘点一次修正」）。

### 4.7 异常处理

| 场景 | 处理 |
|---|---|
| 建单时仓库停用 | `422 {code:1008}` |
| 建单时该仓库无任何库存 | `409 {code:1014}`「无库存可盘」，提示改用单条调整 |
| 提交时实盘行数为 0 | `422 {code:1015}` |
| 追加行的商品不在原快照 | 允许，`book_qty=0`（盘盈典型场景） |
| 追加行的商品已停用 | `422 {code:1004}` 语义提示（停用商品不参与盘点） |
| 过账时某商品被停用/删除 | 整单回滚 `403 {code:1004}`（1004 在错误码表里固定映射 403，与既有出入库的「商品停用」一致）/`404 {code:1006}`，提示先在商品页恢复 |
| 重复审批 | `409 {code:1014}`（非 200，避免 UI 误判成功） |
| 并发过账同一单 | 状态条件更新 `WHERE status='SUBMITTED'` + `rowcount` 判定，第二个请求 409 |
| 明细行超过 2000 | `422 {code:1015}`（与 `post_bill_lines` 的 200 行上限冲突时，分批过账，见下） |

> ★ `post_bill_lines()` 单次上限 200 行（`docs/03` 12'.1）。盘点 800 行有差异时**必须分批**：
> 在**同一个外层事务**内循环调用（`post_bill_lines` 内部 `database.transaction()` 会降级为 SAVEPOINT，T-23 已保证可重入）。
> 分批后仍然是整单原子：任一批失败，外层回滚，全部不落账。

### 4.9 与单条 ADJUST 的关系

两者并存，不合并：

前端在「出入库」页保留现有的「盘点调整」模式（`StockIO.tsx`，对应 `POST /api/stock/adjust`）作为临时纠错入口，
文案改为「单条调整（临时纠错）」；盘点单页另给「按仓库全盘」入口，避免用户走错。

## 5. P0-3 · 业务单据打印

### 5.1 问题

`Labels.tsx` 是唯一实现 `@media print` 的页面，打印的是条码标签。而国内仓库的实际交接全部靠纸：

## 6. P1-4 · 销货单 + 客户对账 + 销售退货

### 6.1 先做决策，再写代码

| 客户类型 | 是否需要 | 说明 |
|---|---|---|
| 内部仓库型（领用为主） | ❌ 不需要 | 领用单已经是出库凭据，做完 P0 即可交付 |
| 贸易 / 商贸型（卖给客户） | ✅ 必须 | 没有销货单就没有"卖给谁、多少钱、退了多少"，客户对账只能靠手抄 |

**售前第一问就是它。** 若不做，销售话术里必须明确「本系统管实物库存，不管销售订单与应收」，避免交付后被追责。

### 6.2 方案

```
销售订单 SO（DRAFT → SUBMITTED → APPROVED）
        │ 审批即过账（与采购入库同构，可部分发货）
        ▼
   出库（OUT 流水，ref_type='SALES_OUT'）── 回写 shipped_qty ── 发满自动 CLOSED
        │
        └── 客户退货 ──▶ 销售退货单 SR（IN 流水，ref_type='SALES_RETURN'）
                              │
                              └── 客户对账单：按客户 + 期间汇总 出 / 退 / 净额
```

- 与采购入库完全同构：`bump_shipped` 用**条件更新**拦超发（仿 `bump_received` 的 `409 {code:1016}`）。
- 单价取 `wms_sales_order_detail.unit_price`；**不**做折扣/税率/优惠（超出仓库职责，留给财务）。
- 对账单只到「金额明细 + 合计」为止，**不出应收凭证、不做账龄、不连开票**（见 2.3 不做项）。

### 6.3 DDL（`db/migrations/0006_wms_sales.sql`）

字段结构与 `wms_purchase_order` / `wms_purchase_in_warehousing` 逐列对齐（含 `is_active`、`status`、
`code`、快照列、`qty`/`shipped_qty`/`price`/`amount`），差异仅在：

| 表 | 与采购侧差异 |
|---|---|
| `wms_sales_order` | `customer_id`（指向 `partners`，须 `type='CUSTOMER'`）；**`warehouse_id` 非空**（出库仓库） |
| `wms_sales_order_detail` | `shipped_qty`（已发数量）替代 `received_qty`（已收数量） |
| `wms_sales_return` / `_detail` | `source_order_id` 可空（允许无单退货）、`return_reason` **必填** |

> ★ 实现时的两处补充（已同步 `docs/02` 5.7 节）：
> 1. **销售订单必须带 `warehouse_id`**：本方案原稿没写这一列，但发货那一刻必须知道从哪个仓扣，
>    否则出库只能再问一次人，且同一客户的货分散在多个仓时无法确定扣哪个。采购订单不需要它（入库单才有仓库）。

>    实际必须挂客户。为此给了单据层一个显式覆盖入口，**没有**放宽 `_resolve_partner` 的类型校验。

`ref_type` 新增两个枚举值：`SALES_OUT` / `SALES_RETURN`（已扩入 `stock_service.BILL_REF_TYPES`），
并同步 `docs/02` 的溯源说明与 `docs/03` 的枚举表。

## 7. P1-5 · 成本核算（移动加权平均）

### 7.1 问题与口径分离

现状：`stock_logs.unit_price` / `amount` 只有入库侧有值（来自采购明细），出库侧为空。
`products.cost_price` 是**参考成本**（人工填），不是账面成本。于是：

- 「库存总表」只有数量没有金额 → 老板第一问答不出。
- 没有出库成本 → 无法算毛利，销货单（P1-4）价值减半。

**两个口径必须分开，不能复用同一列**：

| 列 | 语义 | 谁写 |
|---|---|---|
| `unit_price` / `amount` | 与往来单位的**结算价**（采购价 / 销售价） | 单据明细带过来 |
| `unit_cost` / `cost_amount` | **成本口径**（移动加权单价 × 数量） | 系统算，业务不得填 |

> 不复用 `unit_price` 的原因：采购价含运费/折扣/暂估价，不等于入库成本；
> 且 `trg_logs_immutable` 已锁定 `unit_price`，语义一旦混用，历史数据无法解释。

### 7.2 DDL（`db/migrations/0007_wms_cost.sql`）

```sql
-- 账本加成本口径列（只加列，不动历史行，docs/02 第 6 章铁律）
ALTER TABLE stock_logs ADD COLUMN unit_cost   REAL;   -- 本笔流水的成本单价
ALTER TABLE stock_logs ADD COLUMN cost_amount REAL;   -- 本笔流水的成本金额（= |quantity| * unit_cost）

-- 派生表加移动加权单价（金额 = qty * avg_cost，现算不存，避免第三处真相）
ALTER TABLE stock_current ADD COLUMN avg_cost REAL NOT NULL DEFAULT 0;

-- ★ 必须重建不可变触发器：BEFORE UPDATE OF 的列清单是静态枚举，新增列不在其中就能被改
DROP TRIGGER IF EXISTS trg_logs_immutable;
CREATE TRIGGER trg_logs_immutable
BEFORE UPDATE OF type, quantity, before_qty, after_qty, product_id, warehouse_id,
                 client_msg_id, product_name_snapshot, operator_id, source, created_at,
                 unit_price, amount, unit_cost, cost_amount
ON stock_logs
BEGIN
    SELECT RAISE(ABORT, 'stock_logs 是账本：禁止修改历史行的账目字段（更正请用红字冲销或 ADJUST）');
END;
```

> ★ 这一段是全文档最容易漏的地方：`ADD COLUMN` 之后触发器不会自动覆盖新列，
> 若忘记重建，`UPDATE stock_logs SET unit_cost=0` 就能静默篡改成本，账本保护出现缺口。
> **判据**：任何给 `stock_logs` 加列的迁移，必须同时 `DROP + CREATE` 两个触发器（`trg_logs_no_delete` 不涉及列，可不动）。

### 7.3 计算规则（唯一权威，写进 `rules/10`）

| type | `unit_cost` | `avg_cost` 变化 | 备注 |
|---|---|---|---|
| `IN` | 采购明细单价；期初取 `products.cost_price` | `(qty*avg + q*price) / (qty+q)`；`qty=0` 时直接 `= price` | 入库抬高/摊薄均价 |
| `OUT` | 出库前的 `avg_cost` | **不变** | 出库不动均价 |
| `ADJUST` 正 | 当前 `avg_cost`（为 0 时取 `cost_price`） | **不变** | 盘盈按现均价入账 |
| `ADJUST` 负 | 当前 `avg_cost` | **不变** | 盘亏按现均价出账 |
| 调拨（双流水） | 源仓 `avg_cost` | 源仓不变；**目标仓按该成本重新加权** | 跨仓调拨会改变目标仓均价，这是正确会计行为 |
| 冲销（红字） | **原流水的** `unit_cost` | 反算（IN 冲销要减回，见下） | 冲销入库会降低均价：`avg' = (qty*avg - q*cost)/(qty-q)`，分母为 0 时归零 |

**允许读-算-写的前提**：T-06 禁止"先 SELECT 判断再 UPDATE"，那条针对的是**库存可用性判定**。
成本重算是纯数值换算，不涉及"是否允许"的判断，可以在 `BEGIN IMMEDIATE` 事务内 `SELECT → 计算 → UPDATE`
（SQLite 单写者 + `BEGIN IMMEDIATE` 已串行化）。**必须在代码注释中写明这一区分**，否则后续 review 会误判为违规。

### 7.4 最大风险：`recalc-stock` 必须能重算成本

`docs/02` 铁律说 `stock_current` 是派生表，可全量重算。加了 `avg_cost` 之后，
`manage.py recalc-stock` 若不重算均价，「派生表可重算」这条不变式就被打破，届时账实一致但成本错乱，且无法自愈。

要求：

1. `recalc` 按 `created_at, id` 顺序**重放全量流水**，逐笔重算 `avg_cost` 与 `unit_cost`。
2. 重放结果与现有 `stock_current.avg_cost` 比对，输出 diff（与现有 `qty` diff 同一格式）。
3. `--apply` 前仍强制自动备份（现有行为不变）。
4. 新增不变式检查 6：`stock_current.avg_cost` 重放一致。

|---|---|---|
| GET | `/api/reports/stock-value` | 库存金额表：按仓库/分类汇总 `qty`、`avg_cost`、`amount`；含「成本缺失」标记（`avg_cost=0` 且 `qty>0`） |
| GET | `/api/reports/stock-value/export` | CSV（`utf-8-sig`） |

### 7.6 回归风险清单（本项是全部改动里最高的）

| 风险 | 应对 |
|---|---|
| 所有过账路径都要写成本（`in/out/adjust/sync_batch/post_bill_lines`/盘点/销货/退货/冲销） | 只改 `stock_service` 内部三个原语（`_apply_in`/`_apply_out`/`_apply_adjust`），严禁在各 service 各写一份 |

| 调拨双流水成本串味 | 目标仓 IN 流水的 `unit_cost` 必须取**源仓出库时**的成本，同事务内先出后入 |

## 8. P1-6 · 权限按仓库隔离 + 操作审计

### 8.1 问题

| 现状 | 风险 |
|---|---|
| 只有 `admin` / `operator` 两级（`core/acl.py`） | 多仓/多班组时，A 仓的 operator 能看到 B 仓库存与全部成本价 |
| 无 `audit_logs` 表 | 谁改了商品售价、谁删了供应商、谁改了仓库、谁恢复了备份——全靠猜 |
| `stock_logs` 只记库存账目 | 内控审计问「上月谁把商品成本价从 10 改成 1」，答不出 |

### 8.2 方案

**数据范围**：`user_warehouses` 关联表，空集 = 全部（admin 恒为全部）。

```
services/scope.py:
  warehouse_scope(user) -> list[int] | None   # None = 不限
  assert_warehouse(user, warehouse_id)        # 越权 → 403 {code:1022}
  sql_in(scope) -> tuple[str, list]           # 动态占位符，值仍走 ?
```

**拦截点必须收敛在两处，不得散落**：

1. `services/scope.py: assert_warehouse()`：所有写接口（出入库、调拨、盘点、单据、导入）在 service 入口调用。
2. `models/*_repo.py` 的查询函数：增加 `warehouse_ids: list[int] | None = None` 参数，内部拼
   `AND warehouse_id IN (?,?,...)`。占位符数量由 `len(ids)` 决定，**值仍然参数化**，不违反 T-05。

> ★ 不要试图用 `g.user` 在 model 层偷偷取用户——`models/` 不得知道 HTTP 上下文（分层铁律）。
> scope 一律由 service 解析成 `list[int] | None` 后显式传入。

**成本可见性**：`operator` 默认看不到 `unit_cost`/`avg_cost`/`cost_amount`/`unit_price`。
实现方式与现有「负库存排查仅 admin」一致（`api/reports.py` 已有先例）：在 api 层按角色裁剪字段，
**不要**在 SQL 里用 `CASE` 藏字段（会把口径埋进 SQL）。

**审计**：`audit_logs` 表 + service 层统一入口 `audit_service.record(action, target_type, target_id, before, after)`。

### 8.3 DDL（`db/migrations/0008_scope_audit.sql`）

```sql

    id          INTEGER PRIMARY KEY AUTOINCREMENT,
    actor_id    INTEGER REFERENCES users(id) ON DELETE SET NULL,  -- 允许账号删除后留痕
    actor_name  TEXT    NOT NULL,               -- 快照：账号删了也要知道是谁
    action      TEXT    NOT NULL,               -- 小写点分：product.update / import.commit / backup.restore ...
```

### 新增错误码

| code | HTTP | 含义 |
|---|---|---|
| 1019 | 422 | 导入文件非法（编码 / 表头缺列 / 空数据 / 单元格格式） |
| 1020 | 422 | 导入超限（>5000 行 或 >5 MB） |
| 1021 | 409 | 期初库存已存在（账本非空，不允许重复建账） |
| 1022 | 403 | 无该仓库的数据权限（`user_warehouses` 未授权） |
| 1023 | 409 | 该期间已结账（P2-C 启用后才用，先占位） |
| 1024 | 422 | 成本缺失，无法完成该操作（`avg_cost=0` 且 `cost_price=0` 时的销售毛利计算） |

### 新增陷阱

| 编号 | 陷阱 | 判据 |
|---|---|---|
| T-39 | 导入 CSV 编码：Excel「另存为 CSV」在国内环境默认 GBK，只按 UTF-8 解析会把中文读成乱码且**不报错** | 解码必须 `utf-8-sig` → `gbk` 回退，两者皆失败才报 1019 |
| T-40 | 期初库存重复导入：没有幂等键就会翻倍加库存，且因账本不可删只能逐条冲销 | 幂等键由 `barcode+warehouse_code` 派生；账本非空拒绝（1021） |
| T-41 | 盘点过账用「快照差」而非「实时差」：盘点期间有出库时会把货加回来，账实又错 | `quantity = real_qty - 实时当前值`（详见 4.3） |
| T-42 | 给 `stock_logs` 加列后忘记重建 `trg_logs_immutable`：新列可被静默篡改 | 任何加列迁移必须同时 `DROP + CREATE` 触发器（详见 7.2） |
| T-43 | 权限 scope 拼 `IN` 列表时把 ID 直接格式化进 SQL | 只允许 `",".join("?" * n)` 生成占位符，值走参数（T-05 的延伸） |
| T-44 | 审计 JSON 把 `password`/`token` 写进库 | 写库前过 `core/redact.py` 黑名单，且名单与日志脱敏同源 |
