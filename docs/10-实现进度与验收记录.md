## 二、已实测确认的关键行为

| 风险点 | 验证方式 | 结果 |
|---|---|---|
| 并发出库导致负库存（T-06） | 8 线程同时出库抢 10 件库存 | 成功扣减 ≤ 10、`qty >= 0`、流水合计与扣减量一致 |
| 离线重复入账（T-09） | 同 `client_msg_id` 连续提交两次 | 第二次 HTTP 200 + `duplicated=true`，流水仍 1 条，库存只扣一次 |
| 坏数据拖垮整批（T-08） | 20 条批量同步中塞 1 条未登记条码 | 19 条成功入库，坏条返回 `code:1007`，成功条未被回滚 |
| 事务半途失败 | 注入库存更新异常 | 流水与库存双双回滚，无残留 |
| 账本被删改 | 直接 `DELETE FROM stock_logs` / 改 `quantity` | 均被触发器拦下；回写 `reversed_by`、`remark` 正常放行 |
| 备份残缺（T-04） | 写入后不 checkpoint 即备份，再校验备份内容 | 未落盘数据**包含在备份内** |
| 同秒备份互相覆盖 | 连续两次备份 | 生成两个独立文件（自动追加序号） |
| 备份列表排序 | 混合命名 + 真实时间差 | 最新在前（按解析时间戳，非字典序） |
| SQL 注入（T-05） | `?sort=quantity; DROP TABLE stock_logs; --` | 忽略非法排序列并回落默认，数据未被改动 |
| 时区口径（T-11） | 时间格式与日界断言 | 全部 `+08:00`，`23:59:59` 与次日 `00:00:00` 分属两日 |
| 库存账实纠偏 | 人为篡改账面为 999 → `recalc-stock` | 演练模式抓到差异并退出码 1；`--apply` 先自动备份再修正；`check` 复归通过 |
| 端口占用（PRD 5.8） | 预先占住 5111 再启动 | 自动改用 5112~5115，`/api/ping` 回报的是**实际端口** |
| 全端口耗尽 | 占满 5121~5124 | 抛 `OSError`（由入口层弹窗），不假装成功 |
| 广播失败降级（T-13） | socket 层注入失败 | 状态 `active=false` + 错误原因可见，不抛异常、HTTP 不受影响 |
| 令牌安全（PRD 10.1） | 查库内容 | `api_tokens` 只存 SHA-256 哈希；吊销/过期/账号停用三种情况均拒绝 |

## 三、实现期对文档的修正（文档已同步，此处只列结论）

1. **令牌不可能「复用明文」**——库里只存哈希；改为同设备重登作废旧令牌、发新令牌，**APP 每次登录必须覆盖本地存储**。
2. **条码未命中统一为 `404 + code:1007`**（原文档在同一路径上混用 1006/1007）。
3. **`quantity` 的 CHECK 升级为按 `type` 分别约束**（原来只挡 0，挡不住「负数入库」）。
4. **备份文件名秒级粒度会静默互相覆盖**；**列表排序不能用文件名字典序**（会让人恢复错文件）。
5. **事务原语必须可重入**（嵌套 `BEGIN` 会直接 500）→ 新增 T-23。
6. **waitress 在 `run()` 才 bind**，`port=0` 读不到端口 → 必须自行 bind 后传 `sockets=[...]`；`_quiet`/`async_communications` 非法键。
7. **`login_user()` 只接受用户对象**，传 dict 会在点击登录时才炸 → `auth_service.User`。
8. **登录失败计数是进程级全局状态** → 测试夹具必须 autouse 复位（已写入 PRD 12.4 全局副作用清单）。
9. **补入 `POST /api/products/<id>/restore`**：PRD 要求「复用条码走恢复」，但接口清单当时漏了它，接口总数 33 → 34。

## 七、P0-1：基础数据批量导入 / 导出（2026-10-18）

依据 `docs/14` 第 3 章。落地内容：

| 层 | 文件 | 内容 |
|---|---|---|
| models | `models/import_repo.py`（新） | 逐行 INSERT（`skip_invalid` 要能精确定位坏行）、仓库按「编码或名称」解析、三类导出查询 |
| services | `services/import_service.py`（新） | 编码探测、CSV 解析、三类模板与逐行校验、preview/commit 共用同一套校验、期初幂等提交、导出 |
| services | `services/stock_service.py` | 新增 `opening_stock()` + `opening_msg_id()`；`_write()` 增加可选 `ref_type`（普通扫码仍为 NULL） |
| api | `api/imports.py`（新） | 4 个路由，薄层 |
| 前端 | `pages/ImportExport.tsx`、`api/imports.ts`（新） | 下载模板 → 预检（逐行错误表）→ 确认导入；同页导出 |
| 前端 | `api/client.ts` | 新增 `upload()`（multipart 走同一套认证/包络/1003-1013 跳转） |

**实现期确认的三个关键点**（都已写进代码注释与 `docs/03` 12''）：

1. **先判幂等，再判帐本非空**：同一份期初文件第二次提交必须返回 `duplicated=true`；
   顺序反了会被 `1021` 误拦，`docs/14` 3.9 的验收项就永远过不了。
2. **`ref_id=0` 占位**：`OPENING` 不指向单据，但不变式检查 5 要求 `ref_type`/`ref_id` 同有同无，
   用 0（非 NULL）既满足检查又不伪造单据 id；报表按 `ref_type` 聚合时需单列/排除期初。
3. **`warehouse_code` 接受仓库名称**：`initdb` 建的主仓库没有 `code`，只认编码会让客户第一步就卡住。

**测试**：`tests/test_api_imports.py` 13 项（含 GBK 编码、行号定位、期初幂等、账本非空 1021、
期初仅管理员、文件内重复行、导出 BOM）；全量 `pytest -q` **369 passed**。

**与 `docs/14` 的偏差（1 处）**：方案 3.5 要求「当前库存导出必须含 `qty` 与 `avg_cost`」，
但 `avg_cost` 属 P1-5（`stock_current` 尚未加列）。本次导出只给 `qty`/`updated_at`，
**不拿 `products.cost_price` 冒充账面成本**；P1-5 落地时补列并入导出。

## 五、在本环境验证过的运行方式

```bash
cd desktop
python -m pytest -q            # 275 passed（第二轮后）
python manage.py initdb        # 建库 + 种子
python manage.py check         # 结构/外键/账本不变式自检
python manage.py version
python manage.py runserver     # http://localhost:5000
cd web && npm ci && npm run build   # 产物写入 ../static/spa，必须与代码一起提交
```
