## 第二轮决策：单机桌面程序 → Win7 局域网服务端 + 浏览器客户端（已落地）

起因：交付环境是 **Windows 7 SP1**，而 Win7 上没有 WebView2 运行时，内嵌窗口方案（pywebview）
根本跑不起来；同时要求「开机即服务、局域网内任意机器用浏览器访问」。故整体改为
**纯服务端 exe + Chrome/Edge 浏览器客户端（SPA）**，业务能力一项不减。

### 形态与运行时

| # | 决策 | 取舍依据 | 代价 / 风险 |
|---|---|---|---|
| S1 | 删除 pywebview / pythonnet，主线程直接阻塞在 waitress 上（无窗口、无托盘） | Win7 无 WebView2；且新形态是服务端 | 启动信息只能落盘 + 写日志 + 二维码图片（`core/service_mode.py`） |
| S2 | 运行时线锁定 **Python 3.8.10 + PyInstaller 5.13.2**；waitress 2.1.2 / Pillow 9.5.0 / cryptography 41.0.7 | 3.9+ 安装器与 6.x PyInstaller 都已放弃 Win7 | **真机验收项**（docs/12）；开发机的 3.12 结论不能外推 |
| S3 | 前端受控引入 **Vite 5 + React 18.3.1 + antd 5 + react-router 6 + TypeScript 5**，`package-lock.json` 精确锁定 | 需要组件化控制台界面（表格/表单/弹窗/主题），自研 Fluent 皮肤做不到 | 前端工程只对**构建机**有 Node 依赖；产物提交到 `static/spa`，部署机与打包机都不装 Node |
| S4 | 构建产物入库提交（`desktop/static/spa/`），约定「改前端必须 `npm run build` 后一起提交」 | `pytest`、PyInstaller 打包都不能依赖 Node | 产物未提交 = 白屏（已写成陷阱 T-36 并在 `views/spa.py` 里给人话提示） |
| S5 | 浏览器基线 **Chrome/Edge 109**（Win7 上最高版本），Vite `build.target = chrome88` | antd v5 样式依赖 `:where()`（Chrome 88+） | 若现场是 360/QQ 极速模式（内核 63~87），需按 antd `StyleProvider` 降级并先实测内核版本 |

### 认证与授权

| # | 决策 | 取舍依据 | 代价 / 风险 |
|---|---|---|---|
| A1 | **Flask-Login 会话整体下线**，浏览器端与手机端统一用 `X-Auth-Token` | 两套认证并存最容易「一边拦住了、另一边漏了」；且不用 Cookie → CSRF 天然规避、无需 `form_token` | 刷新页面必须用 `/api/me` 恢复身份；`requirements.txt` 已移除 Flask-Login |
