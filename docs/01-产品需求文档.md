本项目是**局域网内部自用小工具**，不是面向公众的在线服务。标准开发规范中有若干章节按本项目规模**主动降级或标记 N/A**，这是刻意的工程决策，不是遗漏：

| 常规要求 | 本项目处置 | 理由 |
|---|---|---|
| 多租户隔离 | **N/A** | 单账套、单 SQLite 文件，全库即一个租户 |
| HTTPS / TLS | **N/A** | 仅局域网 HTTP；跨网段需求出现时再上反向代理 |
| Redis 缓存层 | **N/A** | 峰值 < 5 QPS，SQLite 索引足够 |
| Docker / K8s 部署 | **N/A** | 交付物是 Windows exe（PyInstaller，onedir） |
| 熔断器 / 降级链路 | **降级为「探测 + 提示」** | 系统唯一外部依赖是局域网内的自身服务 |
| CI/CD 流水线 | **N/A** | 单机开发，本地 pytest + `npm run build` 即门禁 |
| 异地备份 / 主从复制 | **降级为本地多版本备份** | RPO=24h 可接受（见第 14 章） |
| 密码加密 / 注入防护 / 权限校验 / 幂等 / 异常路径 / 日志脱敏 / 自动备份 | **保留，不降级** | 这几条与系统规模无关，属于底线 |

**结论**：本项目按「**局域网自用服务端 + 浏览器客户端**」的标准衡量质量，
重点是把**数据不丢、不重复、不串号**这三件事做扎实，而不是把架构堆复杂度。

## 1. 项目概述与目标

### 1.1 项目背景

市售扫码出入库工具（参考闲鱼「Scanable」）存在三个痛点：数据锁在云端、无法自定义字段、手机与电脑配对流程繁琐。本项目自研一套等价能力的 MVP，用 **UDP 自动发现 + 扫码配对**替代手工输入 IP，用**本地 SQLite 单文件**替代云数据库，目标是自用与小团队场景下完全可控。

### 1.2 V1 核心目标

**一句话定位**：局域网内「手机当扫码枪、电脑当账本」的最小规模出入库闭环。

量化指标（验收口径，全部可测）：

| 编号 | 指标 | 目标值 | 测量方式 |
|---|---|---|---|
| G1 | 配对耗时 | 手机打开 APP 到显示「已连接」≤ 10 秒（同网段） | 人工秒表，连续 3 次取最差值 |
| G2 | 单次扫码入库端到端延迟 | ≤ 800ms（P95） | 浏览器 Network 面板 / APP 日志 |
| G3 | 数据准确性 | 100 笔连续出入库后，`stock_current` 与手工累计一致 | 脚本核对，零差异 |
| G4 | 断网不丢数据 | 手机断网期间 20 笔扫码，恢复后全部成功同步且**不重复入账** | 关 WiFi 实测 |
| G5 | 崩溃数据损失 | 最多丢失最后一次自动备份之后的数据（RPO ≤ 24h） | 见第 14 章 |
| G6 | 打包体积 | 单文件 exe ≤ 60 MB，双击启动到服务可用 ≤ 8 秒 | 冷启动实测 |
| G7 | 开发工期 | 3 个工作日完成电脑端全部 P0/P1 | 里程碑 |

### 1.3 目标用户与角色

| 角色名 | `role` 字段值 | 特征 | 核心需求 |
|---|---|---|---|
| 管理员 | `admin` | 系统搭建者本人或仓管负责人，懂基本电脑操作 | 建商品、配仓库、看报表、备份数据、管账号 |
| 操作员 | `operator` | 仓管员，只用手机或只用电脑收银台式操作 | 扫码入库、扫码出库、查库存，不需要改基础数据 |

设计前提：**1~5 人同时使用**，同一 WiFi/网段，无 AP 隔离。超过 5 人或跨网段属于 V2 边界。

### 1.4 架构设计要点

- **单账套、单文件数据库**：所有业务数据落在一个 `inventory.db` 文件，复制该文件即完成整库迁移，这是自用场景最大的运维优势。
- **双前端、一套 API**：浏览器端是 SPA（Vite + React + antd，产物 `static/spa/`，`X-Auth-Token` 认证）；安卓端只消费 `/api/*` REST 接口（同一套 `X-Auth-Token`）。**两套前端共用同一套认证与同一条接口契约**，会话机制（Flask-Login）已整体下线（docs/09 A1）。
- **服务同进程双职责**：Flask（waitress WSGI）与 UDP 广播线程运行在同一个 exe 进程内，广播线程为守护线程，HTTP 起则广播起，不存在独立进程管理问题。
- **离线优先写入路径**：安卓端本地 Room 队列 → 批量同步接口 → 服务端凭 `client_msg_id` 去重。**幂等是离线设计的生命线**，见 5.5、9.9。

### 2.2 技术选型理由（含两处反直觉决策）

**① 为什么不用 SQLAlchemy / Flask-SQLAlchemy？**
库存写入的正确性依赖一条 SQL 级原子操作：`UPDATE stock_current SET qty = qty - ? WHERE ... AND qty >= ?`（见 9.8）。ORM 会把这层「用受影响行数判断是否扣减成功」的语义包起来，反而更容易写错。表只有 6 张、查询模式固定，Repository + 参数化 SQL 的代码量与 ORM 相当，但可控性更高。**代价**：需自行维护 `schema.sql` 版本号与迁移脚本（见 4.5）。

**② 为什么不用 Pydantic？**
Flask 3 + Pydantic v2 可用，但本项目 API 请求体字段不超过 8 个/接口，手写 `validators.py`（约 150 行）即可覆盖必填、类型、范围、枚举、条码字符集校验，且能返回统一的中文错误文案。打包时少一个 C 扩展依赖，exe 体积与兼容风险都下降。

**③ 为什么用 waitress 而不是 `flask run` / `app.run()`？**
Flask 自带 dev server 明确不用于生产，且 `threaded=True` 下 SQLite 连接管理容易出问题。waitress 是纯 Python、Windows 友好、线程池可控（4~16 线程）、无编译依赖，是 PyInstaller 打包桌面级 Web 服务的事实标准做法。

**④ 为什么浏览器端最终引入 React + antd（推翻第一版的「自研皮肤」决策）**
第一版按「服务端渲染 + 自研 Fluent 皮肤」实现，代价在两项硬需求上暴露：
① 交付机是 Win7 SP1，内嵌窗口方案（pywebview/WebView2）根本不可用，界面只能由浏览器承载，
而浏览器端要做的是**数据密集型企业级控制台**（多列可排序表格、即时校验表单、危险操作二次确认、
抽屉与主题切换），手写 CSS/JS 的边际成本远高于组件库；
② 自研皮肤一旦漏加一个 class，整块区域就掉回浏览器默认态（docs/04 T-31 的原始事故）。
因此改为 **Vite + React + antd 5**，并守住三条边界：
- **只有构建机需要 Node**：产物提交到 `desktop/static/spa/`，`pytest` 与 PyInstaller 打包都不碰 Node；
- **只加必要依赖**：不引入 axios（原生 `fetch` + 一个统一封装）、不引入 Tailwind（antd 自带样式体系）、
  不引入状态管理库（会话状态一个 40 行的 store 足够）；
- **服务端仍是唯一裁判**：界面藏入口不等于挡住，权限、字段校验、业务规则全部在服务端再判一次。

**组件职责**

| 组件 | 职责 | 不做的事 |
|---|---|---|
| UDP 广播线程 | 每 3 秒宣告自身存在，供 APP 自动发现 | 不参与任何业务写入；收不到回包不影响主流程 |
| waitress HTTP | 承载网页与 REST API | 不做跨网段穿透、不做 TLS |
| Service 层 | 业务规则、事务边界、库存扣减 | 不直接 `render_template`、不感知 HTTP |
| Repository 层 | 参数化 SQL、行→字典转换 | 不含业务判断（如「库存够不够」） |
| SQLite（WAL） | 持久化 | 不承担并发队列、不承担缓存 |

### 2.4 服务依赖关系与启动顺序

```
进程启动
  └─ 1. 读取配置（.env / config.ini）        失败 → 使用内置默认值 + 弹窗提示，继续启动
  └─ 2. 初始化 SQLite（建目录、开 WAL、建表）  失败 → 致命，写日志后退出并弹窗
  └─ 3. 启动 UDP 广播线程（守护）              失败 → 仅 WARN，HTTP 照常起（用户可扫码配对兜底）
  └─ 4. 启动 waitress HTTP :5000             端口被占 → 自动尝试 5001~5010，仍失败则致命退出
  └─ 5. 拉起浏览器 / 在系统托盘显示访问地址     失败 → 忽略，日志记录地址
```

关键约束：**步骤 3 必须在步骤 4 之前完成线程创建**，否则 APP 可能探测到「UDP 有响应但 HTTP 还没起」的中间态，误报连接失败。同时 UDP payload 里的端口必须是**实际绑定成功**的端口，不能是配置里的期望端口。

**优雅关闭**：收到 Ctrl+C / 窗口关闭 → 停广播线程 → `waitress` 关闭 → `conn.close()` + `PRAGMA wal_checkpoint(TRUNCATE)`（防止 `.db-wal` 文件残留导致下次启动读到脏状态）。

### 2.5 有状态 / 无状态标注

| 组件 | 状态类型 | 说明 |
|---|---|---|
| waitress HTTP 进程 | 无状态（网页端 Session 除外） | Session 存服务端签名 Cookie，不落库；换机不影响数据 |
| SQLite 文件 | **有状态，唯一真源** | 整库即一个文件，有状态范围完全收敛，备份=复制文件 |
| UDP 广播线程 | 无状态 | 纯宣告，可随时重启 |
| `stock_current` 表 | 有状态，**可由 `stock_logs` 全量重算** | 属派生表，损坏可重建（见 4.5 重建工具），不是单点 |
| 安卓 Room 队列 | 有状态，临时 | 同步成功即清理，丢失可由服务端 `stock_logs` 反向核对 |

### 3.2 数据过滤规则

```python
# 本项目唯一的过滤逻辑在「资源可见性」层面，不在数据范围层面
def check_can_write(user, resource):
    if resource in ("products", "warehouses", "settings", "users", "stock_adjust"):
        return user["role"] == "admin"          # 基础数据与配置：仅 admin
    if resource in ("stock_in", "stock_out", "reports", "barcodes"):
        return True                              # 业务操作：所有已登录角色
    return False

# 唯一需要额外判断的例外：操作员不能编辑「已停用」的商品
def check_product_editable(user, product):
    return user["role"] == "admin" or product["is_active"] == 1
```

```
        token = Header["X-Auth-Token"]
        缺失/未命中 → 401 {code:1003 "登录已失效，请重新扫码配对"}
        命中（查 api_tokens JOIN users，未吊销未过期）→ 更新 last_used_at，注入 g.user
        若 g.user.must_change_password 且路径不在 {/api/me, /api/me/password, /api/logout}
           且该路径确实匹配到真实路由 → 403 {code:1004 "请先修改初始密码"}
  4) else:                            # 页面请求
        放行（交给 SPA 回退 views/spa.py）：浏览器端共用同一套 Token，
        「没登录 → 跳登录页」由前端守卫（RequireAuth）负责，服务端不种会话

需要 admin 的接口:
  require_admin 装饰器 → 不满足返回 403 {code:1004 "该操作仅管理员可执行"}
```

> **两处易错点**（docs/04 T-35）：1003 与 1004 的语义不同，别写反（1003=登录失效会清 Token）；
> 「有没有匹配到真实路由」不能只看 `request.url_rule` —— SPA 兜底路由让它对任何路径都非空。

**防参数绕过**：`/api/*` 的 `product_id`、`warehouse_id` 一律来自数据库查询结果，且写操作前必须校验其存在且 `is_active=1`；不允许信任客户端传来的任意 ID 直接写 `stock_logs`。

### 3.4 前端路由守卫（SPA 侧）

服务端不再做页面级守卫（页面只有一个入口），守卫在前端 `RequireAuth`：

| 前端路由 | 要求 |
|---|---|
| `/login`、`/activate` | 免登录（`/activate` 同时免门禁） |
| `/`、`/stock/*`、`/products`、`/partners`、`/labels`、`/connect`、`/change-password` | 已登录（Token 存 sessionStorage，刷新后用 `/api/me` 恢复） |
| `/warehouses`、`/settings`、`/users`、`/backup` | 已登录 + `role=admin` |

`must_change_password=1` 时前端把除 `/change-password` 外的路由全部重定向到改密页；
**这只是体验优化**，真正的拦截在服务端（3.3 第 3 步），藏入口不等于挡住。
| `/products`、`/customers`（查看） | 已登录 |

未登录访问 → 302 到 `/login?next=`；角色不足 → 渲染 403 页（含「返回上一页」按钮），不静默跳首页（避免操作员误以为自己数据丢了）。

### 3.5 敏感操作二次确认清单

| 操作 | 确认方式 | 附加要求 |
|---|---|---|
| 删除商品 | 输入商品名称完全匹配 | 软删除（`is_active=0`）；若存在流水记录，提示「历史流水将保留」 |
| 删除仓库 | 输入仓库名称完全匹配 | 该仓库有库存余额（`qty≠0`）时**禁止删除**，返回 409 |
| 数据库恢复（用备份覆盖当前库） | 输入当前登录账号密码 | 恢复前**自动先备份当前库**为 `pre_restore_*.db` |
| 重置他人密码 | 输入自己的密码 | 记录审计日志 |
| 吊销设备 Token | 二次确认弹窗 | 记录审计日志 |
| 停用 / 启用账号 | 输入自己的密码 | 会同时吊销该账号全部设备令牌；禁止停用自己与最后一个启用的管理员 |
| 修改监听端口 / 关闭 UDP 广播 | 输入自己的密码 | 提示「修改后 APP 需重新配对」。**接口层必须收口**：把这两项塞进 `PUT /api/settings` 一律 422，否则这道闸一条请求就能绕过 |

普通出入库提交**不做二次确认**（高频操作，加了会被骂），改用「提交后 Toast 显示扣减结果 + 可在流水页撤销」的方式兜底。

## 4. 数据模型

完整 DDL、索引清单、建表顺序见 `02-数据模型.md`（**开发时以该文件的 `schema.sql` 为准，本文只讲设计意图**）。

### 4.1 ER 关系

```
users(1) ──< stock_logs(N) >── (1)products        （操作员维度）
                     │
warehouses(1) ───────┘
                     │
partners(1) ────────<（可选，供应商/客户，nullable）

warehouses(1) ──< stock_current(N) >── (1)products     ← 派生表，可由流水重算

users(1) ──< api_tokens(N)                             ← 安卓设备会话

settings(1)  key-value 配置表，无外键
schema_meta(1) 迁移版本记录，无外键
```

### 4.2 表清单与增长预估

| 表 | 用途 | 预估月增行 | 归档策略 |
|---|---|---|---|
| `users` | 账号 | <1 | 无 |
| `api_tokens` | 设备会话 | <5 | 吊销记录保留 90 天后清理 |
| `warehouses` | 仓库 | <1 | 无 |
| `partners` | 客户/供应商 | <10 | 无 |
| `products` | 商品 | 50~500 | 无（软删除保留） |
| **`stock_logs`** | 库存流水 | **3,000~15,000**（100~500 单/天） | **36 个月后转归档库**：每年初把 >12 个月的流水迁入 `archive_YYYY.db`，主库 `ATTACH` 后按需查历史。年增 1.8 万行、5 年 9 万行，SQLite 单表百万行以内无压力，归档属预防措施而非硬需求 |
| `stock_current` | 当前库存 | 行数=商品数×仓库数（≤5,000 行稳态） | 无 |
| `settings` | 配置 | 常量 20 行内 | 无 |
| `schema_meta` | 迁移版本 | 常量 | 无 |

### 4.3 关键设计决策（逐条讲清「为什么」）

1. **`stock_current` 冗余表保留，不纯靠流水聚合**
   纯流水聚合（`SUM(IN)-SUM(OUT) GROUP BY`）在 15,000 行/月的量级下，仪表盘和扫码页每次都要全量分组，随时间线性变慢。保留冗余表把库存查询变成主键点查（O(log n)），代价是**必须保证一致性**——一致性通过 4.3.2 的事务约束 + 4.5 的重建工具双重保障。

2. **`stock_logs.client_msg_id` 是唯一幂等防线**
   安卓端离线时先生成 UUID 存本地，同步时带上。服务端 `UNIQUE(client_msg_id)`，重复提交直接返回首次结果而非报错（见 5.5）。**没有这个字段，离线同步必然导致重复入账**——这是本项目最容易出致命 bug 的地方。

3. **时间统一存 ISO-8601 `TEXT`，不用 Unix 时间戳、不用 SQLite `DATETIME`**
   `TEXT` 形如 `2026-10-15T17:30:12+08:00`，人读友好、字典序=时间序（可直接 `ORDER BY created_at`）、跨语言解析无歧义、备份文件可直接用文本编辑器抽查。语义统一为**东八区本地时间**（自用场景「今日入库量」必须按本地日历日切分，用 UTC 会导致每天 8 点前统计口径跳变）。

4. **主键统一 `INTEGER PRIMARY KEY AUTOINCREMENT`**
   不用 UUID 做主键：SQLite 下整型主键即 rowid，点查与外键 JOIN 更快、索引更小。UUID 只在 `client_msg_id`、`token`、`trace_id` 这类需要客户端预生成的场景使用。

5. **软删除 + `UNIQUE(barcode)` 的冲突处理**
   商品软删除（`is_active=0`）后，若同条码再次新增会撞唯一约束。规则：**软删除的商品条码永久占用，不允许复用**；确需复用由 admin 走「恢复该商品」而非新建。这条规则必须写死，否则会出现「一个条码两条商品」的数据串号事故。

6. **`stock_logs.type` 增加第三种取值 `ADJUST`**
   原始设计只有 IN/OUT。但盘点场景（实物与账面不符）无法用 IN/OUT 表达，强行用会造成流水语义失真。`ADJUST` 表示账面校正，`quantity` 可正可负，且**仅 admin 可发起**。这是相对原始蓝图的增补，属 P1。

### 4.4 空值与默认值语义

| 场景 | 规则 |
|---|---|
| 数据库 `NULL` | 表示「未填写」，只用于语义上真可空的字段（`partners.id`、`unit_price`、`expires_at`、`deleted_at`） |
| 数值可空字段 | `quantity`、`qty`、`cost_price` **禁止 NULL**，无值即 0；否则流水聚合结果为 NULL 会污染报表 |
| Python 层 | 读出 `None` 一律在 Repository 层显式处理，禁止依赖 `or 0` 之类的隐式转换（`0 or None` 类陷阱） |
| JSON 输出 | `NULL` → JSON `null`，禁止省略字段（安卓 Retrofit data class 依赖字段存在性，省略会解析失败） |
| 前端展示 | `null` → `—`；`0` → `0`。二者展示不同，禁止统一成空字符串 |

### 4.5 迁移策略（无 ORM，自建极简版）

不引入 Alembic（对 6 张表是负担）。自建方案：

```
schema_meta(version INTEGER, applied_at TEXT)  ← 记录已到版本
db/migrations/0001_init.sql        基线
db/migrations/0002_xxxx.sql        后续每次变更一个文件，编号递增、禁止改历史文件
启动时：读 schema_meta.version → 顺序执行 version 更大的迁移文件 → 事务内更新 version
```

规则：迁移文件**必须幂等可失败回滚**（单事务执行，失败即整体回滚并终止启动，不允许「带病启动」）；每次改表必须同步更新 `schema.sql`（全量基线）与 `schema_meta` 目标版本，二者不一致时**以 migrations 顺序执行结果为准**。

**库存重算工具**（P1，必做）：`python manage.py recalc-stock` —— 按流水全量重算 `stock_current`，并逐行 diff 输出差异报告。这是 4.3.1 冗余表设计的必备配套，也是排查「库存对不上」的第一手段。

### 4.6 大表迁移注意

`stock_logs` 是唯一可能变大的表（5 年约 9 万行）。SQLite 的 `ALTER TABLE ADD COLUMN` 是 O(1) 元数据操作，可直接用；但 `ALTER TABLE ... ADD CONSTRAINT` 语法不支持，需要「建新表→拷数据→改名」四步走，此时**必须先停 HTTP 服务**（自用单进程，天然满足）。给 `stock_logs` 加索引一律用 `CREATE INDEX IF NOT EXISTS`，并在迁移注释中标注预计耗时。

## 5. 功能模块详细说明

每模块统一包含：功能描述 / 业务规则 / 正常流程 / 异常处理 / 数据流向 / 幂等性 / 并发控制。

### 5.1 登录与会话

**功能**：网页账号密码登录；安卓端账号密码换取长期 Token。

**业务规则**
- 初始账号 `admin` / `admin123`（用户明确要求）。首次登录**强制改密**，改密前除「修改密码」外所有路由拦截。
- `admin123` 属弱口令，因此启用登录保护：同一用户名连续失败 5 次锁定 15 分钟；同一 IP 连续失败 20 次锁定 15 分钟。锁定期间返回 `429 {code:1005}`，提示剩余等待秒数。
- 密码策略：至少 8 位，须含字母与数字；哈希 `pbkdf2:sha256:600000`；禁止空密码账号。
- 「记住密码」= 浏览器记住表单（不自建明文存储）；网页 Session 有效期 12 小时；安卓 Token 默认 90 天，可续期。

**正常流程**：输入账号密码 → 校验 → 写 `last_login_at` → 网页种 Session / 安卓返回 Token → 跳仪表盘 / APP 进首页。

**异常处理**

| 情形 | 用户看到 |
|---|---|
| 用户名不存在 / 密码错 | 同一句「账号或密码错误」（不区分，避免账号枚举），失败计数 +1 |
| 账号被禁用 | 「该账号已停用，请联系管理员」 |
| 锁定期内 | 「失败次数过多，请 XX 秒后再试」 |
| 首次登录未改密 | 顶栏常驻红色提示条 + 强制跳转改密页 |
| Token 过期 / 被吊销 | APP 收到 401 + `code:1002` → 自动回到配对页并清除本地 Token |

**数据流向**：`/login`（POST 表单）→ `services/auth.py:authenticate()` → `models/user_repo.py:find_by_username()` → `werkzeug.security.check_password_hash` → `users` 表。

**幂等**：登录天然幂等，重复提交仅刷新 `last_login_at`。
**并发**：失败计数写 `settings` 或内存字典（重启即清）；单进程场景取**内存 + 落日志**，明确告知重启会解除锁定。

### 5.2 仪表盘

**功能**：登录后首页。卡片：商品总数、库存总件数、今日入库件数/笔数、今日出库件数/笔数、库存预警清单（`qty < min_stock`）、最近 10 条流水、服务状态（IP:端口 / UDP 广播状态 / 最近备份时间）。

**业务规则**
- 「今日」= 服务器本地日历日 `[今日 00:00:00, 明日 00:00:00)`，按 `created_at` 字符串前 10 位切分。
- 库存总件数 = `SUM(stock_current.qty)`，**含负数**（负数意味着数据异常，必须原样展示并在预警区标红，不得 `MAX(0,...)` 掩盖）。
- 预警清单上限 50 行，超出提示「共 N 条，查看完整清单」跳报表页。

**数据流向**：`/dashboard` → `render_template` → 模板内嵌 4 次查询（`services/dashboard.py:summary()`）→ `products` / `stock_current` / `stock_logs`。

**异常处理**：查询抛错 → 页面顶部黄条「部分数据加载失败：<原因>」，其余卡片正常渲染（不整页 500）。无数据 → 卡片显示 `0` 与「暂无记录」，首次使用引导文案「先去新增商品」。

**性能**：4 个查询全部走索引（见 02 文档索引清单），预期 < 50ms。禁止在模板里写循环查库（N+1）。

### 5.3 基础数据管理（商品 / 仓库 / 客户供应商）

**商品字段**：`name`(必填,≤100)、`barcode`(唯一，可空=无条码商品)、`category`(≤30)、`unit`(≤10，默认「件」)、`cost_price`(≥0,2 位小数)、`sale_price`(≥0)、`min_stock`(≥0,默认 0)、`remark`、`is_active`。

**业务规则**
- 条码规范化：录入时 `strip()` + 全角转半角 + 去空格，长度 3~48，字符集仅 `[0-9A-Za-z\-]`。不合规直接 422，**不自动修正**（自动修正会让用户以为存进去了却查不到）。
- 重复条码：新增/编辑时先查 `barcode`，冲突返回 409 并展示已存在商品的名称与 ID；含已软删除商品。
- 编辑商品**不影响**历史流水（流水存 `product_id`，商品名变更不回溯改流水文本快照；`stock_logs` 需冗余存 `product_name_snapshot`，见 02 文档，否则历史报表会随改名失真）。
- 删除商品 = 软删；软删后不出现在下拉选择，但流水与报表仍可查到。
- 仓库删除前置校验：`EXISTS(SELECT 1 FROM stock_current WHERE warehouse_id=? AND qty!=0)` → 禁止，409。

**异常处理**：表单校验失败 → 保留已填内容 + 字段级红字（不整页清空）；无数据 → 表格「暂无数据 + 新增按钮」；删除被拒 → 弹窗列出原因（哪个仓库还有多少库存）。

**数据流向**：`/products` 列表页 → `services/product_service.py` → `models/product_repo.py` → `products` 表。

**幂等**：网页表单提交带 `form_token`（一次性随机串）防重复提交；安卓侧靠 `client_msg_id`。
**并发**：商品编辑加 `updated_at` 乐观校验——提交时带原 `updated_at`，与服务端不一致则 409「该商品已被他人修改，请刷新后重试」（P1；单人编辑场景发生概率低，但实现成本仅一个 WHERE 条件，值得做）。

### 5.4 入库 / 出库（核心）

**功能**：表单 = 商品（条码扫码/输入/下拉选择）+ 数量 + 仓库 + 备注（+ 出库可选客户 / 入库可选供应商）→ 提交。

**业务规则（最关键章节）**
1. 数量 `quantity` 必须是**正整数**，范围 1~100,000；小数直接 422。
2. 出库**必须够扣**：库存不足直接拒绝，返回 422 并附当前库存值与差额（「库存不足：当前 3 件，本次需 5 件，缺口 2 件」）。
3. 一次提交 = 一个事务：写 `stock_logs` + 更新 `stock_current`，任一失败整体回滚。
4. 扣减 SQL 用条件更新（原子）：
   ```sql
   UPDATE stock_current SET qty = qty - ?, updated_at = ?
    WHERE product_id = ? AND warehouse_id = ? AND qty >= ?;
   ```
   `cursor.rowcount == 0` → 判定为库存不足 → `ROLLBACK`。这是唯一正确的实现方式，**禁止**「先 SELECT 判断再 UPDATE」（有竞态窗口）。
5. 入库时 `stock_current` 不存在记录则 `INSERT OR IGNORE` 建行再累加（upsert 两步法，见 04 文档陷阱 T-07）。
6. `ADJUST`（盘点）：直接设定目标值，`quantity = 目标 - 当前`，可正可负；仅 admin；备注必填。
7. 撤销错误单据：提供「红字冲销」——生成一条等额反向流水，`remark` 记 `REVERSAL_OF:#<原ID>`，原行 `reversed_by` 指向冲销行。**禁止物理删除流水**，且该约束由数据库触发器 `trg_logs_no_delete` / `trg_logs_immutable` 强制（外键 RESTRICT 只挡父表删除，挡不住删流水，故必须靠触发器；见 02 文档）。

**正常流程**：选/扫条码 → 命中商品（未命中见异常）→ 填数量 → 提交 → 服务端事务写入 → 返回 `{code:0, data:{log_id, product_name, after_qty}}` → 前端 Toast「入库成功，当前库存 25 件」→ 清空数量、保留仓库选择、焦点回条码框（连续扫码优化）。

**异常处理**

| 情形 | 用户看到 |
|---|---|
| 条码未登记 | 弹窗「条码 6901234567890 未找到」+ 两个按钮：〔新增该商品〕（预填条码）/〔忽略〕 |
| 库存不足（出库） | 字段红 + 「当前库存 3 件，缺口 2 件」，不自动改为 3（禁止「尽力扣减」，会让账实不符） |
| 商品已停用 | 「该商品已停用，不能出入库」，引导 admin 恢复 |
| 网络中断（网页） | 表单内容保留在 `sessionStorage`，恢复后提示「有未提交草稿」 |
| 重复提交 | 第二次返回首次结果（幂等），Toast 追加「（重复提交已合并）」 |
| 服务未启动（APP） | 「未连接到电脑，请点击重新配对」+ 保留本地待同步队列 |

**幂等性**：所有出入库接口**必须**支持 `client_msg_id`（UUID，≤36 字符，全局唯一）。服务端 `INSERT ... UNIQUE` 冲突时：不报错，查询原记录并返回 `code:0, data.duplicated:true`。网页端由前端生成 UUID，安卓端由 Room 生成。**未传 `client_msg_id` 的接口调用一律 422 拒绝**（强制必填，杜绝「忘了传」这条退路）。

**并发控制**：SQLite 写锁串行化 + 上述条件更新原子扣减 + `busy_timeout=5000`。5 人同时扫码时写操作排队，最坏等待 200ms 级，可接受。`stock_current` 不加 `version` 字段（派生表，写入全走原子 SQL，无「读-改-写」用户交互窗口）。

### 5.5 离线缓存与同步（安卓契约，本期定义接口）

**规则**
- 安卓 Room 队列表 `pending_ops`：`client_msg_id` PK、`type`、`barcode`、`quantity`、`warehouse_id`、`remark`、`created_local_at`、`sync_status`(`PENDING`/`SYNCED`/`FAILED`)、`retry_count`、`last_error`。
- 同步：`POST /api/sync/stock-logs` 批量提交（单次 ≤ 200 条，超出 APP 自行分页）。
- 服务端逐条处理，**单条失败不回滚整批**，返回逐条结果数组（`{client_msg_id, ok, code, msg}`）。整批事务 vs 逐条事务的取舍：自用场景更在意「不因一条坏数据卡住整批」，故取**逐条独立事务**。
- `FAILED` 且 `retry_count ≥ 5` → APP 停止自动重试，转人工处理列表（可编辑数量后重投）。
- 服务端返回 `duplicated:true` 的条目，APP 标记为 `SYNCED`（已达最终一致）。

**异常**：条码不存在 → 该条 `FAILED(code:1007)`，APP 展示「该条码电脑端未登记，请先在电脑端新增商品」；仓库不存在 → `FAILED(code:1008)`；Token 失效 → 整批返回 401，APP 不清队列，回到配对页。

### 5.6 报表查询

**流水查询**：筛选 = 日期区间（默认今日，最大跨度 366 天）、条码/商品名（模糊）、仓库、类型、操作员；分页 20/50/100 默认 20；排序默认 `created_at DESC`。导出 CSV（UTF-8 **带 BOM**，否则 Excel 打开中文乱码——高频坑，见 T-10）。
**库存现状**：按仓库×商品矩阵，支持「只看低于最低库存」，合计行。
**汇总报表**：按日/商品/分类聚合入库出库件数与金额（`qty × unit_price`），默认最近 30 天。

**异常**：跨度超限 → 422 并提示「最多查询 366 天，请缩小范围」；空结果 → 「未查到记录，试试放宽日期」；导出 > 50,000 行 → 拒绝同步导出，提示「请分段导出」（自用场景不引入异步任务框架，明确降级）。

### 5.7 条码生成与打印

生成 Code128 矢量图（`barcode.ClassCode128`）→ 输出 SVG/PNG → 页面以「标签网格」布局（每行 N 个，含商品名 + 条码 + 可读文本）→ 浏览器 `Ctrl+P` 打印，`@media print` 隐藏导航与按钮。可打印张数 1~50，默认 1。

**业务规则**：无条码商品支持「生成内码」——以 `S` + 10 位补零 ID 形式（如 `S0000000123`），确保与厂商条码（EAN/UPC 纯数字）不冲突，并允许后续用真实条码覆盖（覆盖时校验新条码唯一）。
**异常**：商品无条码且未生成内码 → 打印页提示并给〔一键生成内码〕；打印机未就绪 → 无法感知，文档明确告知「打印预览为唯一判据」，建议先 A4 预览再选标签纸。

### 5.8 连接服务（UDP 广播 + 配对二维码）

**UDP 广播**
- 线程每 3 秒向 `255.255.255.255:55555` 发送 `SO_BROADCAST` 报文。
- Payload（UTF-8，**行式协议**，非 JSON，便于 Android 端零依赖解析）：
  ```
  INVENTORY_SERVER v1.0 IP:192.168.1.10 PORT:5000 NAME:仓库电脑
  ```
  字段以空格分隔，`KEY:VALUE` 形式；`NAME` 含空格则整段截断到最后一个空格（协议约定 `NAME` 必须放最后，见 04 文档 T-12）。
- 本机 IP 枚举：遍历所有网卡，取 `192.168.`/`10.`/`172.16~31.` 私有网段且非 `127.` 的第一个；多网卡时按「默认路由优先」选择，并在设置页展示全部候选 IP 让用户手选（这解决「虚拟机网卡被误选导致 APP 连不上」这一高频事故）。
- 变更检测：端口绑定成功后才启动广播；广播内容变化（IP 变动）时立即补发一次。

**配对二维码**：内容为 JSON（`{"protocol":"inventory_server","version":"1.0","host":"192.168.1.10","port":5000,"name":"仓库电脑","token_hint":"可选配对码"}`），页面 `img[src=data:image/png;base64,...]` 展示；APP 扫到即自动填 host/port，无需手输。

**异常处理**
| 情形 | 表现 |
|---|---|
| 无可用网卡 IP | 广播线程不启动，状态栏红字「未检测到局域网 IP，请检查网络连接」，二维码仍可显示 127.0.0.1（本机浏览器可用） |
| UDP 发送失败（防火墙拦截） | 状态栏黄字「自动发现不可用，请用手机扫配对二维码」，**HTTP 不受影响** |
| 端口 5000 被占用 | 自动改试 5001~5010，广播实际端口；全失败则弹窗报错并退出 |
| APP 收到广播但 HTTP 不通 | APP 侧 3 次重试后提示「电脑已发现但无法连接，多为路由器 AP 隔离，请改用扫码配对或关闭隔离」 |

**AP 隔离兜底链路**：UDP 发现失败 → 扫配对二维码（仍走 HTTP，同网段可用）→ 手输 IP:端口 → 三档全部失败则判定跨网段/隔离，提示改用热点同网段方案。

### 5.9 系统设置

- 通用：监听 IP/端口、UDP 广播开关与间隔、本机名称、时区固定 Asia/Shanghai（只读展示，不开放修改）。
- 数据：手动备份按钮、备份目录、自动备份开关（默认开，每日 03:00）、保留份数（默认 7）、库存重算、从备份恢复。
- 账号：改自己密码、admin 可管理账号与吊销设备。
- 关于：版本号、数据库路径、当前 `schema_meta.version`、日志目录。

所有设置写 `settings` 表（key-value，`updated_at`）；改端口/广播间隔需重启生效，页面必须显式提示「需重启后生效」，禁止「改了没反应」的不明状态。

### 7.2 列表页统一规范

- 分页：`?page=1&page_size=20`，`page_size` 白名单 `{20,50,100}`，非法值回落 20；`page` 超总页数返回空列表（不报错、不自动回首页）。
- 排序：`?sort=created_at&order=desc`，`sort` 必须在**服务端白名单**内（防 SQL 注入，见 T-05），白名单外的值忽略并用默认排序。
- 搜索：模糊用 `LIKE '%' || ? || '%'` 参数化；商品搜索同时匹配 `barcode`（精确优先）与 `name`（模糊）。
- 空状态、加载中（表单提交按钮置灰 + spinner）、失败重试三种状态每个列表页都必须有。

### 7.3 核心用户流程

**流程 A — 仓管员手机端入库（全自动配对）**
手机打开 APP → 监听 UDP 55555 → 收到 `IP:192.168.1.10 PORT:5000` → 点「发现电脑，点击连接」→ APP 调 `/api/ping` 确认 → 弹登录 → 存 Token → 首页点「入库扫码」→ 对准条码 → ZXing 识别 → 震动+滴声 → 显示商品名与当前库存 → 输入数量 → 提交 → Room 落库 `PENDING` → Retrofit 即时上传 → 成功则 `SYNCED`，失败保持 `PENDING` → Toast「已入库 5 件，当前 30 件」。

**流程 B — 电脑端网页出库**
浏览器 `/stock/out` → 光标自动在条码框 → 扫码枪输入条码回车 → 自动带出商品 → 填数量 → 选客户 → 提交 → 原子扣减 → Toast 展示剩余库存 → 焦点回条码框，仓库保持。

**流程 C — 断网续传**
手机关 WiFi → 连续扫 20 笔 → 队列 20 条 `PENDING` → 首页显示「20 条待同步」红标 → 开 WiFi → 自动触发批量同步 → 逐条返回 → 20 条转 `SYNCED` → 电脑端流水页可查到 20 条 `source=APP` 记录，且不重复。

### 7.4 前端路由守卫
见 3.4。SPA 已不再使用 `?next=`：登录成功后由前端直接跳转，
外部地址既不会被回显也不会被跳转（开放重定向问题随该参数一起消失）。

### 7.5 弱网与离线兜底（浏览器端）
- **扫码台草稿暂存**：仓库选择与入库/出库模式写 `localStorage`，刷新页面不丢（一个班次基本只在一个仓库）；
- **条码录入保留现场**：提交失败（库存不足 / 条码未登记）后**保留条码与数量**，用户改一个数字就能重交；
- **`client_msg_id` 一次提交生成一次、成功才清空**：网络抖动重试时服务端才能认出是同一笔（T-09）；
- 提交中按钮置灰（配合服务端幂等，双保险）；失败提示带追踪码，不做静默失败。

### 8.1 认证约定
- **浏览器端与安卓端共用同一套**：`POST /api/login` 换取 `token`，后续所有 `/api/*` 请求带请求头 `X-Auth-Token`；Token 失效统一 `401 {code:1003}`。

## 9. 并发与性能

### 9.1 峰值流量估算（用公式，不拍脑袋）

设计上限：**5 个用户同时操作**（3 台手机 + 2 台电脑网页）。
- 单人连续扫码极限节奏：每 3 秒 1 笔 → 0.33 QPS/人。
- 5 人同时 = **1.7 QPS**。写请求占 60% ≈ **1 QPS 写入**。
- 集中触发场景：手机开机后队列批量同步。单台一次性推 200 条 = 1 个请求（批量接口），5 台同时推 = 5 QPS **请求**，但服务端展开为 1000 次事务 → 瞬时 **200 事务/秒** 是最坏压力点。
- 结论：常规负载远低于瓶颈；**唯一需要专门设计的是批量同步风暴**。

### 9.2 并发承载分析

| 操作 | 同时人数 | 处理方式 | 预期响应 | 结论 |
|---|---|---|---|---|
| `/api/ping` | 20 | 无锁读 | <5ms | 无压力 |
| 商品列表 | 5 | 读，WAL 不阻塞写 | 30~80ms | 无压力 |
| 扫码查商品 | 5 | 主键/唯一索引点查 | <10ms | 无压力 |
| 单笔入库/出库 | 5 | 写事务，SQLite 串行 | 20~150ms | 无压力 |
| 批量同步 200 条 ×5 | 5 | **单连接串行** | 见 9.5 | **需限流** |
| CSV 导出 5 万行 | 1 | 流式生成 | 3~10s | 拒绝并发（见 5.6） |
| 库存重算 | 1 | 全表重算 | 0.5~3s | 仅限 admin，执行期加互斥锁 |

### 9.3~9.4 缓存策略
**N/A（不引入 Redis/进程内缓存）**。理由：5 QPS 下 SQLite 索引点查已 <10ms，加缓存层只会引入「缓存与 `stock_current` 不一致」这一新故障模式，收益为负。唯一可接受的「缓存」是浏览器 HTTP 缓存静态资源（`static/` 设 `Cache-Control: max-age=86400`）。若未来变慢，优化顺序：加索引 → 改查询 → 才考虑进程内 TTL 缓存（商品/仓库字典表，TTL 60s + 写后立即失效）。

### 9.5 批量同步的保护措施（唯一的真瓶颈点）
- 单批上限 **200 条**（超出返回 422，APP 需分页）。
- 同步接口在**同一事务**内处理整批 → 把 200 次 fsync 降为 1 次，这是最关键的优化。
  - 与 5.5「逐条独立事务」冲突吗？不冲突：**批内单条失败仅回滚该条**用 SAVEPOINT 实现（每批一个外层事务 + 每条一个 savepoint），兼顾 fsync 次数与错误隔离。此为强制实现方式，见 T-08。
- 全局串行：`sync_lock = threading.Lock()` 保护 `/api/sync/*`，同一时刻只允许 1 个同步批次执行，其余排队（等待 >10s 返回 503 + `Retry-After: 5`，APP 退避重试）。
- 预期：200 条 ≈ 40ms~200ms，5 台串行 ≈ 1s 内全部完成。

### 9.6 数据库连接配置

| 项 | 值 | 说明 |
|---|---|---|
| 连接模型 | **每请求一个连接**（`teardown_appcontext` 关闭） | 严禁全局共享连接（`check_same_thread` 陷阱 T-01） |
| `journal_mode` | `WAL` | 读写不互斥 |
| `synchronous` | `FULL` | **不降级为 NORMAL**。自用系统宁慢不丢，NORMAL 在断电时可能丢最近事务 |
| `busy_timeout` | `5000` ms | 写锁排队 |
| `foreign_keys` | `ON` | **每连接必须显式开**（SQLite 默认关，T-02） |
| `isolation_level` | `None`（手动 BEGIN/COMMIT） | 避免 Python 隐式事务时机不可控 |
| 线程池 | waitress `threads=8` | 8 线程 × 1 连接 ≤ SQLite 承受范围 |

### 9.7 限流规则
仅两处需要：登录接口（同用户名 5 次/15min、同 IP 20 次/15min）、同步接口（全局 1 并发 + 每分钟 ≤30 请求/设备）。其余接口不做限流（局域网内部，加限流只影响自用体验）。

### 9.8 锁使用场景
| 场景 | 手段 | 不用另一种的原因 |
|---|---|---|
| 库存扣减 | SQL 条件更新（原子） | 读-改-写有竞态窗口 |
| 商品编辑 | `updated_at` 乐观校验 | 悲观锁需长事务持锁，交互编辑场景不合适 |
| 批量同步 / 库存重算 / 恢复备份 | 进程内 `threading.Lock` | 单进程，跨进程锁过度设计 |

### 9.9 幂等性设计汇总

| 接口 | 机制 | 重复调用的行为 |
|---|---|---|
| `/api/stock/in`、`/out`、`/adjust` | `client_msg_id` UNIQUE | 返回首次结果 + `duplicated:true`，**不报错** |
| `/api/sync/stock-logs` | 同上（逐条判定） | 该条标记 `ok:true, duplicated:true` |
| `/api/stock/reverse/<id>` | 原流水上打 `reversed_by` 标记 + 条件更新 | 已冲销返回 409，绝不生成第二条冲销 |
| `/api/products` | `barcode` UNIQUE | 409 + 冲突商品信息 |
| `/api/login` | 天然幂等 | 复用同设备名下的有效 Token（避免 Token 无限增长） |
| 网页表单 | 一次性 `form_token` | 重复提交丢弃并提示 |

## 10. 安全设计

### 10.1 五层防护（按局域网场景裁剪）

| 层 | 措施 | 具体实现 |
|---|---|---|
| 网络 | 只监听局域网、不暴露公网 | 启动时检测绑定 IP 是否私有网段，公网 IP 直接拒绝启动并提示；README 明确「禁止端口映射到公网」 |
| 网络 | 安全响应头 | `after_request` 统一加 `X-Content-Type-Options: nosniff`、`X-Frame-Options: SAMEORIGIN`、`Referrer-Policy: same-origin`、`Content-Security-Policy: default-src 'self'; img-src 'self' data:; style-src 'self' 'unsafe-inline'` |
| 应用 | 认证分派 | 见 3.3，白名单最小化 |
| 应用 | SQL 注入 | **一律参数化**；表名/列名/排序字段只能来自服务端白名单常量；禁止 f-string 拼 SQL（CI 检查，见 T-05） |
| 应用 | XSS | Jinja2 默认转义；`\| safe` **必须**经 `markupsafe.escape` 审计，全局仅允许白名单一处（条码 SVG 内联，需先正则校验只含 `[0-9a-zA-Z<>/=" #.,%-]`） |
| 应用 | CSRF | 网页端所有写操作用 POST + `form_token`；安卓端走 Header Token（天然免疫） |
| 应用 | 参数校验 | 集中 `services/validators.py`，每个接口声明字段类型/必填/范围/长度/字符集；未通过 422 |
| 应用 | 错误页不泄密 | 生产 `TEMPLATE_DEBUG=false`，500 只返回通用页 + `trace_id`，堆栈仅入日志 |
| 数据 | 密码 | `pbkdf2:sha256:600000`，加盐不可逆；首次登录强制改密 |
| 数据 | Token | 存 `api_tokens` 表为 **SHA-256 哈希**，明文只在响应里出现一次；数据库泄露不等于凭据泄露 |
| 数据 | 备份文件 | `backups/` 目录权限：Windows 下提示用户勿放共享盘；文档注明备份含明文数据，需同等保护 |
| 运维 | 依赖扫描 | 每月 `pip-audit`；版本锁定，禁止 `>=` |
| 运维 | 日志脱敏 | 见 10.4 |
| 密钥 | 生命周期 | 本项目无外部 API Key；`SECRET_KEY` 首次启动随机生成并写入 `config.ini`（不入代码库），轮换会使全部网页 Session 失效，需在文档告知 |

### 10.2 明确不做的安全措施（避免误解）
HTTPS（无公网）、字段级加密（无 PII：不存身份证/银行卡/完整手机号）、WAF、防重放签名、IP 白名单。若未来接公网，第 28 章「V2 规划」列了升级路径。

### 10.3 API 错误码

| HTTP | `code` | 含义 | 客户端处理 |
|---|---|---|---|
> **三个最容易用错的码**（docs/03 1.3 有完整的语义边界）：
> - `1003` 专指「登录/Token 失效」，客户端收到会**清 Token 跳登录页**；
>   因此「某个字段里的口令打错了」**禁止**用它，必须用 `1002 / 422 + data.errors`。
> - `1004` 同时承担「角色不足」与「需先改密」，两者客户端处理一致（提示并返回，不清 Token）。
> - `1013` 必须由前端**主动**引导去激活页，**不得**自动重试、不得清 Token。

| HTTP | `code` | 含义 | 客户端处理 |
| 400 | 1001 | 请求格式错误 / JSON 解析失败 | 提示「请求异常」 |
| 422 | 1002 | 字段校验失败（`data.errors` 为字段→原因数组） | 表单字段级红字 |
| 401 | 1003 | 未登录 / Token 无效或过期 | APP 清 Token 回配对页；网页跳登录 |
| 403 | 1004 | 无权限（角色不足 / 需改密 / 账号停用） | 提示并返回 |
| 429 | 1005 | 登录失败次数过多 | 展示 `data.retry_after` 秒 |
| 404 | 1006 | 资源不存在 | 「商品/仓库不存在或已删除」 |
| 404 | 1007 | 条码未登记（实现期修正：属查找未命中，语义应是 404；业务码 1007 仍驱动 APP 的「去新增」流程） | APP 引导去电脑端新增 |
| 422 | 1008 | 仓库无效或已停用 | 提示切换仓库 |
| 422 | 1009 | **库存不足** | `data` 含 `current`、`lack`，展示缺口 |
| 409 | 1010 | 唯一约束冲突（条码重复 / 已冲销） | 展示冲突对象 |
| 409 | 1011 | 乐观锁冲突（数据被他人修改） | 提示刷新重试 |
| 503 | 1012 | 同步通道繁忙 | 按 `Retry-After` 退避 |
| 403 | 1013 | 软件未激活（离线授权，见 `11-第三方软件接入指南.md`） | 提示到电脑端激活页完成激活，不重试 |
| 500 | 1999 | 服务内部错误 | 展示 `trace_id`，引导查日志 |

### 10.4 日志规范

JSON 行式（每行一个对象），字段：`ts`（ISO-8601 东八区）、`level`、`trace_id`、`user_id`、`username`、`action`（如 `stock.out`）、`source`（`WEB`/`APP`）、`ip`、`duration_ms`、`status`、`err_code`、`err_msg`、`extra`。

| 级别 | 场景 |
|---|---|
| INFO | 登录/登出、每笔出入库（**业务审计主链路，必须记**）、备份、设置变更、同步批次结果 |
| WARN | 库存不足被拒、幂等命中、Token 失效、UDP 发送失败、登录失败 |
| ERROR | 未捕获异常、事务回滚、写库失败、备份失败 |
| CRITICAL | 数据库损坏、端口绑定失败致无法启动、迁移失败 |

**脱敏（硬规则）**：`password`、`password_hash`、`X-Auth-Token`、`token`、`SECRET_KEY` 在任何日志与异常输出中必须替换为 `***`；实现为日志过滤器按 key 名黑名单屏蔽，**不依赖开发者自觉**。

链路追踪：`before_request` 生成 8 位 `trace_id`（优先取请求头 `X-Request-ID`）→ 注入日志上下文 → `after_request` 回写响应头。用户报错时报这 8 位即可定位。

轮转：`RotatingFileHandler`，单文件 10 MB × 保留 10 个，目录 `logs/`。级别默认 INFO，`config.ini` 可临时调 DEBUG（文档警示不要常开）。保留期：INFO 30 天、ERROR 90 天（按文件名时间判断，超期删除）。

### 10.5 PII 与合规
本系统不采集自然人身份信息（无身份证/手机号/银行卡）。`partners` 表可填联系人电话——属用户自主录入的业务数据，文档需提示「请勿录入与服务无关的他人个人信息」，数据仅存本地磁盘、不出局域网、不上云。

> 这章是给 AI 编程工具的「踩坑预警」。完整的陷阱清单（T-01~T-38，含已作废项）与对策在

> 本轮新增的高频坑：**T-32**（PyInstaller 5.x 产物没有 `_internal`）、

### 12.1 类型统一规约（违反即返工）

| 维度 | 全局唯一规定 | 禁止 |
|---|---|---|
| 时间 | `TEXT`，ISO-8601 **东八区带偏移**：`2026-10-15T17:30:12+08:00`，生成统一用 `services/timeutil.py:now_iso()` | 禁止 `datetime.now()` 裸调用、禁止混用 UTC、禁止 Unix 秒、禁止 SQLite `CURRENT_TIMESTAMP`（它存 UTC 且无时区，是本项目最大定时炸弹） |
| 主键 | `INTEGER PRIMARY KEY AUTOINCREMENT` | 禁止 UUID 做主键 |
| 客户端标识 | `client_msg_id` TEXT(36) UUID | — |
| 金额 | `REAL`，2 位小数，入库前 `round(x,2)` | 禁止浮点做累加求和展示「分」（报表金额允许 REAL，但需在 UI 注明「金额按 2 位小数展示」） |
| 数量 | `INTEGER`。`IN`/`OUT` 恒正（方向由 `type` 表达）；`ADJUST` 可正可负（=目标−当前，负即盘亏） | 禁止 REAL；禁止用 `IN`+负数表达出库；`quantity != 0` 及按 type 的正负规则由 DDL CHECK 强制（见 02 文档） |
| 布尔 | `INTEGER` 0/1 | 禁止 `true/false` 文本 |
| 枚举 | 全大写：`IN`/`OUT`/`ADJUST`、`CUSTOMER`/`SUPPLIER`、`WEB`/`APP`/`PDA`、`PENDING`/`SYNCED`/`FAILED`；角色例外用小写 `admin`/`operator`（沿用原始蓝图） | 禁止同一字段大小写混用；写库前统一 `.upper()`（角色除外） |
| NULL 语义 | 见 4.4 | 禁止用空字符串表达「无」 |

### 12.2 框架组合已知陷阱（Day1 必须先验证）
1. **PyInstaller + Flask 模板/静态文件路径**：冻结后 `__file__` 在临时解包目录，必须用 `sys._MEIPASS` 兼容函数（`core/paths.py:resource_path()`）。忘记 = 双击 exe 报 `TemplateNotFound`。
2. **PyInstaller + waitress**：需 `--hidden-import waitress` 及其子模块，否则 `ModuleNotFoundError`。
3. **PyInstaller + python-barcode**：默认字体与 `config` 目录需手工加进 `datas`，否则 `FileNotFoundError`。
4. ~~**Flask 3 + Flask-Login 0.6.3**：`user_loader` 必须返回带 `is_authenticated` 的对象~~ ——
   **已作废**：Flask-Login 随 Jinja 页面一起下线（docs/09 A1），浏览器端与手机端统一走 `X-Auth-Token`。
5. **`sqlite3` + 多线程**：连接不能跨线程共享；`check_same_thread=False` 只用于单连接串行场景，本项目走「每请求一连接」，见 T-01。
6. **WAL 在网络盘（SMB/NAS）上不可靠**：exe 放共享盘运行会随机 `database is locked` 甚至数据损坏 → README 硬性要求「程序与数据库必须放本地磁盘」。
7. **`socket` 广播在某些网卡不生效**：`255.255.255.255` 与子网定向广播（`192.168.1.255`）行为不同，实现需先试子网定向广播、失败回落全局广播。
8. **waitress `port=0` 读不到真实端口**：它到 `run()` 才 bind，届时 `_server_ports` 仍为空，回报端口会是 0（APP 连 0 端口必然失败）。自己 `bind((host,0))` 取端口后用 `create_server(sockets=[sock])`（`sockets` 与 `host`/`port` 互斥）；`_quiet`、`async_communications` 在 waitress 3.0 不是合法 adjustment 键。
9. ~~**Flask-Login 只接受用户对象**：`login_user(dict)` 会抛 `AttributeError`~~ —— **已作废**（同上）。
   替代要点：浏览器端 Token 只存内存 + sessionStorage，刷新页面必须用 `GET /api/me` 恢复身份，
   否则会表现为「刷新一下就被踢回登录页」。
   另注：局域网走 `http://192.168.x.x` 属于**非安全上下文**，`crypto.randomUUID` 在 Chrome 里不存在，
   生成 `client_msg_id` 必须有降级实现（见 `web/src/api/client.ts:newClientMsgId`）。
10. **`transaction()` 必须可重入**：批量同步是「外层事务 + 每条自己的事务」形状，嵌套再发 `BEGIN` 会报 `cannot start a transaction within a transaction`；检测到 `conn.in_transaction` 时自动降级为 SAVEPOINT（见 04 文档 T-08）。

**Day1 门禁**：写第一个功能代码之前，必须先跑通「`app.py` 最小启动 + 一个 pytest 用例 + PyInstaller 打一次包并双击能出页面」。这条不满足不许往下写业务。

### 12.3 外键依赖与操作顺序
- 建表/插入顺序（依赖正序）：`schema_meta → users → api_tokens → warehouses → partners → products → stock_logs → stock_current → settings`。
- 测试数据清理顺序（依赖逆序）：`stock_logs → stock_current → products → partners → warehouses → api_tokens → users`。
- 级联策略（逐表标注，理由必须写进 DDL 注释）：
  - `api_tokens.user_id` → **CASCADE**（删用户即踢设备，无保留价值）
  - `stock_logs.product_id/warehouse_id/operator_id` → **RESTRICT**（流水是账本，禁止因删主数据而消失或悬空）
  - `stock_current.product_id/warehouse_id` → **CASCADE**（纯派生数据，可随主数据清理）
  - `stock_logs.partner_id` → **SET NULL**（客户删了，流水仍要保留）
- 因此「删除商品」实际实现是软删；物理删除只对**无流水**的商品开放（admin，且需二次确认）。

### 12.4 全局副作用清单与测试隔离

| 副作用 | 隔离方案 |
|---|---|
| SQLite 数据库文件 | 每个测试用 `tmp_path` 独立库文件，`conftest.py` fixture 自动建表 + 种子数据，测试结束删文件 |
| UDP 广播线程 | 测试环境 `BROADCAST_ENABLED=false`（由 `config` 注入），**禁止**测试里真发广播包 |
| 文件系统（备份、日志、条码图） | 全部路径来自 `core/paths.py`，测试用 `tmp_path` monkeypatch |
| 环境变量 / `config.ini` | fixture 里 `monkeypatch.setenv`，用完自动恢复 |
| 全局 `threading.Lock` | 模块级单例，测试中显式重新构造 app factory 以获得新锁 |
| `SECRET_KEY` | 测试固定值，不随机 |

**App Factory 强制**：`create_app(config=Config)` —— 测试与生产用同一工厂、不同配置类。**禁止模块级 `app = Flask(__name__)` + 全局副作用**（那样测试无法隔离，也无法注入配置）。`conftest.py` 的清理 fixture 必须在写第一个测试之前设计好。

### 12.5 本地与生产差异对照

| 维度 | 开发（`python app.py`） | 生产（双击 exe） | 踩坑点 |
|---|---|---|---|
| 资源路径 | 项目相对路径 | `sys._MEIPASS` 临时目录 | `TemplateNotFound`、字体缺失 |
| 可写数据路径 | 项目内 `data/` | `%LOCALAPPDATA%\ScanableSelf\` | 把 exe 放 `Program Files` 时**无法写自身目录**（UAC 虚拟化），必须用 AppData 或同目录可写检查 |
| 控制台 | 有 stdout | `-w` 无窗口 | 异常看不见 → 必须写日志文件 + `sys.excepthook` 弹窗 |
| 依赖来源 | pip 环境 | 冻结进 exe | hidden-import 缺失、DLL 缺失 |
| 配置 | `.env` | `config.ini`（AppData） | `.env` 在 exe 模式下不可靠（用户拿不到） |
| 端口占用 | 少见 | 5000 常被其他软件占用 | 必须实现自动换端口（5.8） |
| 防火墙 | 已放行 | 首次运行弹 Windows 防火墙授权 | **用户点「取消」→ UDP 静默失败**，必须在状态栏自检并提示 |
| 时区 | 本机 | 本机 | 用户改系统时区会改变「今日」口径 → `timeutil` 固定 +08:00 |
| 数据量 | 几十条 | 数万条 | 报表/流水必须分页，禁止全量渲染 |

### 12.6 数据库注意事项
- 迁移多分支合并：**不适用**（单人开发，迁移文件线性编号即可；但规则保留——「禁止修改已应用的迁移文件」）。
- 事务边界：**「写流水 + 更新库存」必须在同一事务**，这是本项目唯一的事务铁律。任何跨表写都按此判断。
- `PRAGMA` 必须每连接设置（`foreign_keys`、`busy_timeout` 不在文件里持久化）。
- 禁止 `SELECT *`：Repository 必须显式列名（防字段变更静默改变语义）。

### 14.1 仓库结构（Monorepo）
```
scanable-wms/
├── CODEBUDDY.md              # AI 编程工具入口（每次会话自动加载）
├── .codebuddy/               # 规则 / 子代理 / 自定义指令

├── android/                  # 安卓端（本期仅骨架 + 契约引用）
└── README.md
```
单仓库理由：双端契约（API/UDP 协议）强耦合，同仓可保证文档一致性；自用项目无权限分隔需求。

### 14.2 电脑端交付形态（Windows exe）

**服务端形态（交付形态）**：双击 exe 即启动 HTTP 服务与手机发现广播，**不弹任何窗口**；
启动信息（局域网访问地址、访问二维码、防火墙命令、并发建议）由 `core/service_mode.publish()`
落盘 + 记日志；局域网内任意机器用浏览器打开该地址即可使用，**不需要安装任何客户端软件**。

**开发运行**
```bash
cd desktop && python -m venv .venv && .venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env         # 填 SECRET_KEY 留空即自动生成
python manage.py initdb        # 建库 + 种子 admin
python manage.py runserver     # http://localhost:5000
pytest -q                      # 门禁

cd web && npm ci && npm run build   # 改过前端才需要：产物写入 ../static/spa（必须与代码一起提交）
```

**打包**
```bash
pyinstaller ScanableSelf.spec          # 用 spec 而非命令行，便于加 datas/hidden-imports
# 产出 dist/ScanableSelf/ScanableSelf.exe（onedir：交付物是整个 dist/ScanableSelf/ 目录）
# ⚠ 只认 dist 下这个。build/ScanableSelf/ScanableSelf.exe 是中间产物，双击会报找不到 Python DLL；
#   打包完顺手删掉 build/ScanableSelf/。
# ⚠ PyInstaller 5.13.2（Win7 线）的 onedir 产物**没有 _internal 子目录**，
#   DLL 与 datas 直接落在 dist/ScanableSelf/ 下 —— 别按 6.x 的手册去找（docs/04 T-32 第 5 条）。
```
`.spec` 必须包含：`datas=[('templates','templates'), ('static','static'), ('db/schema.sql','db'), ('db/migrations','db/migrations'), (license 公钥,'keys'), (barcode 字体,'barcode/fonts')]`
——其中 **`static` 里含 `static/spa` 的 SPA 构建产物，漏了就是打开白屏**（docs/04 T-36）；
`hiddenimports=['waitress','waitress.task','waitress.channel','waitress.server','qrcode','qrcode.image.pil','barcode','barcode.writer','barcode.codex'] + collect_submodules('api') + collect_submodules('views') + ['services.backup_service']`（后三项是动态导入的蓝图，静态分析看不见，漏了会 `No module named 'api.ping'`）；`excludes=['pkg_resources','setuptools']`；`console=False`（无控制台；无窗口形态，界面由浏览器承载）+ 一个 `console=True` 版带控制台供排查。坑的排查手法见 `docs/04` T-32（T-33/T-34 的 pywebview 内容已作废）。

**运行时数据落点**（关键决策）
| 内容 | 路径 | 理由 |
|---|---|---|
| 程序 | 任意目录（用户可放桌面） | — |
| 数据库 / 备份 / 日志 / 配置 | `%LOCALAPPDATA%\ScanableSelf\` | 放 `Program Files` 时目录不可写（UAC）；放同目录会让用户换 exe 版本时数据混乱 |
| 首次运行 | 自动创建目录 + 建库 + 迁移 | 用户零配置 |

**升级与回滚**：exe 自身无状态，但产物是 onedir → 升级 = 覆盖 `dist/ScanableSelf/` 整个目录（数据在 AppData 不受影响）→ 回滚 = 放回旧目录。规则：**新版本若含迁移，必须先自动备份再迁移**，迁移失败则拒绝启动并提示「用旧版 exe + 最新备份」。

### 14.3 多环境
自用项目只有「开发」与「发布」两态，差异仅在 `Config` 类（`DevConfig` 开 DEBUG、`ProdConfig` 关）与打包 spec。无 Staging。

### 14.4 安卓端（本期只列契约）
Release 签名 APK；权限：`CAMERA`、`INTERNET`、`ACCESS_WIFI_STATE`、`ACCESS_NETWORK_STATE`、`VIBRATE`；Android 9+ 需在 `networkSecurityConfig` 允许局域网明文 HTTP（`<domain-config cleartextTrafficPermitted="true">` 按网段配置，**不要**全局 `usesCleartextTraffic=true`）。

## 15. 架构韧性

### 15.1 单点故障识别

| 组件 | 是否单点 | V1 接受 | V2 消除方案 |
|---|---|---|---|
| 电脑（exe 进程） | **是** | ✅ 接受（自用） | 云端多端同步 / 双机热备 |
| `inventory.db` 单文件 | **是** | ✅ 接受 | 定时同步副本到网盘/第二磁盘 |
| 局域网路由器 | **是** | ✅ 接受 | 兜底：热点直连模式 |
| waitress HTTP | 是 | ✅ | 多进程（无必要） |
| UDP 广播 | 是 | ✅ | 已有扫码/手输 IP 三级兜底 |
| SQLite 写锁 | 是 | ✅（5 QPS 够用） | WAL + 队列化写 |

**唯一的硬风险是「电脑本地磁盘坏 = 数据全丢」**，因此第 15.3 备份策略按 RPO 24h 设计，且要求备份**可手动导出到 U 盘/网盘**。

### 15.2 故障影响矩阵

| 故障 | 完全不可用 | 降级可用 | 不受影响 |
|---|---|---|---|
| 电脑关机/进程崩溃 | 网页全部、APP 全部在线功能、打印 | APP 本地历史与扫码（写本地队列）| APP 已同步数据 |
| HTTP 端口被占换端口 | APP（旧端口缓存）| 网页（新端口）| 数据 |
| UDP 广播失败（防火墙/隔离）| 自动发现 | 扫码配对、手输 IP | 全部业务 |
| SQLite 文件损坏 | 全部写入 | 只读（若有备份）| APP 离线记录 |
| 磁盘满 | 写入、备份、日志 | 读取查询 | APP 本地 |
| 网络断开（同机使用）| APP | 网页（localhost）| — |

### 15.3 RTO / RPO 与备份

| 指标 | 取值 | 落地 |
|---|---|---|
| **RPO** | ≤ 24 小时 | 每日 03:00 自动备份（进程内线程，非 cron）+ 关键操作前手动备份按钮 + 迁移前强制备份 |
| **RTO** | ≤ 30 分钟 | 恢复流程 = 复制备份文件到数据目录 + 启动 exe（有 `/backup` 页向导），文档化到运维手册 |

备份实现：用 **`sqlite3` 的 `backup()` API**（在线一致性快照），**禁止**直接 `copy inventory.db`（WAL 模式下主文件不含未checkpoint 数据，拷出来是残缺的 → 高频致命坑 T-04）。命名 `inventory_YYYYMMDD_HHMMSS[_trigger].db`，**同秒冲突自动追加序号**（`_2`…）——实现期实测发现秒级时间戳会让「手动 + 自动」同秒触发的两次备份互相覆盖，等于静默丢掉一份快照。备份列表按**文件名里的时间戳**倒序（不用文件名字典序：带/不带 `_manual` 后缀的同秒文件会排错序，而列表排错序会直接让人恢复错文件）。保留最近 7 份 + 每月首份保留 12 个月。备份成功/失败都写日志；失败时在仪表盘红条告警（自用项目「静默失败」是最坏的失败模式）。

### 15.4 熔断器
**基本 N/A**（无外部 API 依赖）。唯一保留：APP 侧对 `/api/sync/*` 返回 503 的退避（连续 3 次 503 → 暂停 60s 自动同步，转手动触发），避免死循环打爆电脑。

### 15.5 自动恢复

| 故障 | 方案 |
|---|---|
| 进程崩溃 | Windows 服务化不做（复杂度过高）；提供 `ScanableSelf.bat` 崩溃后 5 秒重启循环，README 教如何配任务计划程序开机自启 |
| SQLite `database is locked` | `busy_timeout=5000` + 单连接串行 + 事务尽量短（不跨用户交互持事务） |
| 端口占用 | 自动 5001~5010 递增重试 |
| WAL 残留 / 未干净关闭 | 启动时执行 `PRAGMA integrity_check`（<10ms 级），异常则拒绝写并提示恢复 |
| 断电后启动 | 同上 integrity_check + `wal_checkpoint(TRUNCATE)` |
| 磁盘 <500MB | 启动检测 + 仪表盘告警 + 拒绝备份 |

### 15.6 优雅降级层级

| 级别 | 触发 | 可用功能 | 用户看到 | 运维动作 |
|---|---|---|---|---|
| L0 正常 | 全好 | 全部 | 无提示 | — |
| L1 部分降级 | UDP 广播失败 | 全部（发现能力丧失） | 状态栏黄条「自动发现不可用，请扫码配对」 | 检查防火墙 |
| L2 部分降级 | 自动备份连续失败 3 次 | 全部 | 仪表盘红条「数据备份已停止，请立即手动备份」 | 查磁盘/权限 |
| L3 核心降级 | 库存自检不一致（重算 diff≠0） | 可读；写入需 admin 确认 | 顶栏橙条「库存数据异常，已启动重算建议」 | 跑 `recalc-stock` |
| L4 紧急降级 | `integrity_check` 失败 | 全部停写 | 启动即弹「数据库可能损坏，已切换只读，请从备份恢复」 | 恢复备份 |

## 16. 跨系统状态一致性

**支付/外部交易：N/A**（系统不涉及资金与外部交易）。

本项目的「跨端一致性」问题是 **APP 本地队列 ↔ 服务端流水**，机制：
1. **唯一标识**：`client_msg_id` 由 APP 生成（UUID v4），服务端 UNIQUE 约束。
2. **确认即清理**：只有收到 `code:0`（含 `duplicated:true`）才把本地条目置 `SYNCED`；网络异常/超时**不得**清理。
3. **超时不等于失败**：同步请求超时后，APP **必须重发同一 `client_msg_id`**（幂等保证不会重复入账），而不是标记失败——这是关键规则，与「超时即失败」的直觉相反。
4. **每日对账**：APP 提供「核对」入口，拉 `/api/stock/logs?date=今天&source=APP` 与本地记录按 `client_msg_id` 比对，差异列表展示（P1）。
5. **人工兜底**：`retry_count≥5` 的条目转「需处理」列表，可编辑数量/删条码后重投，或直接删除（须提示「该笔不会入账」）。

**服务端内部一致性**：`stock_logs` 与 `stock_current` 同事务写入；派生表可全量重算；`recalc-stock` 是最终仲裁工具，其 diff 报告是排查唯一依据。

### 28.2 UI 默认方案

**Ant Design 5 企业级控制台风格**（组件库随前端构建链引入，见 2.1；**不用 CDN，产物自带**）：

| 项 | 取值 |
|---|---|
| 主色 / 功能色 | `#1677FF`（主）/ `#4096FF`（浅）/ `#0958D9`（深）；成功 `#52C41A`、警告 `#FAAD14`、错误 `#FF4D4F` |
| 背景 / 容器 | 页面 `#F5F5F5`、卡片 `#FFFFFF`、次级 `#FAFAFA`；深色由 `theme.darkAlgorithm` 统一生成 |
| 文字 | 主 `#1F1F1F`、次 `#595959`、弱 `#8C8C8C` |
| 圆角 / 字体 | 全局 `borderRadius: 6`；`PingFang SC` → `Microsoft YaHei` → `Segoe UI` → `system-ui`；正文 14px / 标题 24px·600 |
| 间距 | 8px 栅格 + 4/8/12/16/24 阶梯（信息密度优先，不堆留白） |
| 数值列 | 一律 `.sd-num`（右对齐 + `tabular-nums` 等宽数字），金额固定 2 位小数 |
| 动效 | 表格行 150ms 背景过渡、Modal/Drawer 用 antd 默认缓动；**不使用大幅位移或视差** |
| 图标 | `@ant-design/icons`（随包，无 CDN）；所有纯图标按钮必须带 `aria-label` |

**应用外壳**（`web/src/layout/AppShell.tsx`）：左侧固定导航 208px（分组 + 图标 + 选中胶囊；<992px 收成 64px 图标条，<768px 变抽屉）
＋ 顶栏 56px（系统名、当前用户、主题切换、退出）
＋ 内容区（`#F5F5F5` 底上的白色卡片）
＋ 底部状态栏 32px（广播状态、服务器地址、连接状态、追踪码、时钟）。

**深浅色**：`ConfigProvider` + `theme.darkAlgorithm` 一键切换，默认跟随系统并记忆到 `localStorage`。
★自绘部分（顶栏、状态栏、登录卡片）必须同步覆盖 `[data-theme="dark"]` 下的一组 CSS 变量 ——
antd 组件会跟着算法变，自绘的部分不会，漏了就在深色里冒出几条白带。

**页面级规范**：列表页统一「分页 20/50/100 + 空状态 + 加载骨架屏 + 失败可重试」；
表单失焦即校验、错误就地标红（字段级错误来自 `data.errors`）；
危险操作（恢复备份、重置密码、停用账号、冲销）一律 Modal 二次确认；
成功提示 3s 自动消失，**错误提示常驻并带追踪码**（供报障时对日志）。

**文件分工**：`web/src/styles/global.css`（自绘外壳与打印规则）、
`web/src/api/client.ts`（唯一的接口出口：注入 Token、解包包络、1003/1013 跳转、Toast 化错误）、
`web/src/store/session.ts`（Token 与当前用户）、`web/src/layout/*`（外壳与守卫）、
`web/src/pages/*`（逐页组件）。

> 2026-10 调整一：原「Bootstrap 5.3 默认主题」已废弃（并删除全部 Bootstrap 依赖）。
> 2026-10 调整二：中间版的自研 **Fluent 2 / Windows 11 皮肤已整体作废** ——
> 交付机 Win7 没有 WebView2、内嵌窗口方案不可用，界面改由浏览器承载，
> 而浏览器端要做的是数据密集型控制台，自研 CSS 的边际成本远高于组件库（见 2.2 ④ 与 docs/09 U3）。
> 仍然成立的教训（换到 antd 上照样适用）：**样式优先挂容器/祖先，别让「漏加一个 class」决定一块区域的成败**（docs/04 T-31）。

### 28.3 告警规则（自用 = 页面提示，不引入通知通道）
| 条件 | 提示位置 |
|---|---|
| 自动备份连续失败 3 次 | 仪表盘红条 + 日志 CRITICAL |
| `integrity_check` 异常 | 启动弹窗 + 只读模式 |
| 库存预警（`qty<min_stock`） | 仪表盘列表 + 商品列表标记 |
| 磁盘 <500MB | 仪表盘黄条 |
| UDP 发送失败 | `/connect` 页黄条 |
| 负库存（异常数据） | 仪表盘红字，必须排查 |

### 28.5 交接要点
新接手者最小阅读集：`CODEBUDDY.md` → 本文第 0、4.3、12、13 章 → `02-数据模型.md` → `03-API接口规范.md`。必须口头/文档交接：`SECRET_KEY` 与数据目录位置、历史事故、为什么不用 ORM。

### 28.6 数据合规
数据全部存本地、不出局域网、不上云、无第三方共享。用户自主录入的联系人信息应由用户自行确保来源合法。系统提供备份导出能力，导出文件含业务数据，需同等保护。
