# 04 · 开发规约与已知陷阱

> **写第一个功能代码之前必读。** 每条陷阱都有编号，代码审查与提交信息可引用（如 `fix: 按 T-02 补 foreign_keys pragma`）。
> 严重度：🔴 会导致数据错误或交付失败 · 🟡 会导致体验/运维问题 · 🟢 规范一致性

---

## A. 陷阱清单（T-01 ~ T-33）

### 🔴 T-01 · `sqlite3` 跨线程共享连接
**症状**：`ProgrammingError: SQLite objects created in a thread can only be used in that same thread`，或加了 `check_same_thread=False` 后出现随机数据错乱、游标串位。
**根因**：waitress 是 8 线程模型，一个全局连接被多线程共用。
**对策**：**每请求一连接**。`models/database.py` 用 `g` 缓存当前请求连接，`teardown_appcontext` 关闭。
```python
# 正确
def get_connection():
    if "db" not in g:
        conn = sqlite3.connect(db_path(), isolation_level=None)
        _apply_pragmas(conn)      # T-02/T-03
        g.db = conn
    return g.db

@app.teardown_appcontext
def close_db(exc=None):
    conn = g.pop("db", None)
    if conn is not None: conn.close()
```
**禁止**：模块级 `conn = sqlite3.connect(...)` 全局单例。

### 🔴 T-02 · `PRAGMA foreign_keys` 默认关闭
**症状**：外键约束形同虚设，能写入不存在的 `product_id`，产生孤儿流水，事后 `foreign_key_check` 才发现。
**对策**：该设置**不持久化**，必须每次 `connect` 后执行。已封装在 `_apply_pragmas()`，测试 fixture 同样必须走它（否则测试通过、生产失败）。

### 🔴 T-03 · `synchronous=NORMAL` 的诱惑
**症状**：写快 3~5 倍，看起来"优化成功"。断电/进程被杀时可能丢失最近已提交事务，WAL 甚至可能损坏。
**对策**：本项目**固定 `FULL`**。自用系统的核心资产是账本，不接受任何性能换安全的优化。若嫌慢，优化路径是批量事务合并（T-08），不是降同步级别。

### 🔴 T-04 · 用文件复制做 SQLite 备份
**症状**：`copy inventory.db backup.db` 后恢复，报「数据库损坏」或**静默丢最近数据**。
**根因**：WAL 模式下未 checkpoint 的数据在 `inventory.db-wal`，只拷主文件必然残缺；且写入瞬间拷贝得到撕裂页。
**对策**：必须用在线备份 API：
```python
src = sqlite3.connect(db_path()); dst = sqlite3.connect(backup_path)
with dst: src.backup(dst, pages=1, progress=_progress_cb)
src.close(); dst.close()
```
恢复后校验：`PRAGMA integrity_check` 返回 `ok` + 关键表 `COUNT(*)` 符合预期（UT-19）。

### 🔴 T-05 · 动态 SQL 拼接（含排序字段）
**症状**：`?sort=qty;DROP` 之类直接执行，或 `ORDER BY ${sort}` 被注入。
**对策**：
1. 值一律 `?` 参数化；**表名/列名/排序方向**只能来自服务端白名单常量映射：
```python
SORT_WHITELIST = {"created_at": "created_at", "quantity": "quantity"}   # 显式映射，非拼接
def build_order(sort, order):
    col = SORT_WHITELIST.get(sort)
    if col is None: col, order = "created_at", "desc"      # 非法值静默回落，不报错
    return f"ORDER BY {col} {'ASC' if order=='asc' else 'DESC'}"
```
2. 全项目禁止 f-string/`%`/`format` 拼 SQL（`/cr` 审查子代理会 grep `execute(f"` 与字符串 `+` 拼接）。

### 🔴 T-06 · 出库用「先查再改」判断库存
**症状**：单用户测试一切正常；两台手机同时出库同一商品，各查到 3 件、各扣 3 件 → 库存变 -3。
**对策**：唯一正确写法是条件更新 + `rowcount` 判定（01-PRD 5.4 规则 4）。UT-06 用 8 线程并发抢 10 件库存回归验证。

### 🔴 T-07 · `INSERT OR REPLACE` 更新 `stock_current` 的隐式删除
**症状**：`INSERT OR REPLACE` 触发 `ON DELETE CASCADE`（`stock_logs` 对它是 RESTRICT，但 REPLACE 本质是 DELETE+INSERT），或重置未列出的列。
**对策**：upsert 用两步法，禁止 `INSERT OR REPLACE`：
```sql
INSERT OR IGNORE INTO stock_current(product_id, warehouse_id, qty, updated_at) VALUES (?,?,'0',?);
UPDATE stock_current SET qty = qty + ?, updated_at = ? WHERE product_id=? AND warehouse_id=?;
```

### 🔴 T-08 · 批量同步逐条提交导致 200 次 fsync
**症状**：200 条同步耗时 8s+，且每条独立事务期间其它写入被 `busy_timeout` 阻塞排队。
**对策**：**外层单事务 + 每条 SAVEPOINT**，兼顾 fsync 次数与错误隔离：
```python
conn.execute("BEGIN IMMEDIATE")
for log in batch:
    conn.execute("SAVEPOINT sp")
    try:
        _apply_one(log); conn.execute("RELEASE sp")
    except BizError as e:
        conn.execute("ROLLBACK TO sp"); conn.execute("RELEASE sp")
        results.append(fail(e))
conn.execute("COMMIT")      # 一次 fsync 落整批
```
注意 `BEGIN IMMEDIATE`（立刻拿写锁）而非 `BEGIN DEFERRED`，避免中途升级锁失败。
★ **`transaction()` 原语必须可重入**（实现期实测撞出 500）：批量同步是「外层事务 + 每条各自的事务」这种形状，
  嵌套时若再发 `BEGIN`，SQLite 直接报 `cannot start a transaction within a transaction`。
  正确做法是检测到 `conn.in_transaction` 时自动降级为 `SAVEPOINT`/`RELEASE`/`ROLLBACK TO`，
  且**内层失败只能回滚内层**，绝不能把外层已写的流水一起带走。参考 `models/database.py:transaction()`。

### 🔴 T-09 · 把 `client_msg_id` 做成可选
**症状**：某端忘传 → 服务端走「无幂等」分支 → 网络抖动重发即重复入账，且难以复现（只在弱网出现）。
**对策**：字段**必填**，缺失直接 422 拒绝。宁可让开发期立刻发现，也不要留静默路径。这是本项目最重要的一条 API 约定。

### 🔴 T-10 · CSV 无 BOM，Excel 打开中文乱码
**对策**：导出首字节写 `\ufeff`，编码 `utf-8-sig`；换行 `\r\n`。测试断言前两字节。

### 🟡 T-11 · `datetime.now()` / `CURRENT_TIMESTAMP` 的时区与格式漂移
**症状**：SQLite `CURRENT_TIMESTAMP` 存的是 **UTC 且无时区**（`2026-10-15T09:30:12`），与 Python 本地时间混存 → 「今日入库」在早 8 点前统计错乱，报表对不上。
**对策**：
1. 时间**一律由 Python 生成**，禁止用 SQLite 默认时间函数；
2. 统一入口 `services/timeutil.py:now_iso()` → `datetime.now(ZoneInfo("Asia/Shanghai")).isoformat(timespec="seconds")`；
3. 「今日」判定用 `substr(created_at,1,10) = ?` 前缀比较（字典序=时间序，且能用上索引）；
4. 代码审查 grep 清单：`utcnow`、`datetime.now()`（无参数）、`CURRENT_TIMESTAMP`、`localtime`。

### 🟡 T-12 · UDP 报文中 `NAME` 含空格破坏解析
**对策**：协议规定 `NAME` 置于行尾（见 03-API 8.1），解析取 `NAME:` 之后全部；新增字段必须插在 `NAME` 之前。测试 UT-18 覆盖含空格中文名。

### 🟡 T-13 · `255.255.255.255` 全局广播在部分路由器/网卡不生效
**对策**：先尝试**子网定向广播**（`192.168.1.255`，由本机 IP + `/24` 掩码推算），失败回落全局广播；两者都失败则状态栏提示改用扫码配对（L1 降级），绝不静默。

### 🟡 T-14 · 多网卡时选到虚拟网卡 IP
**症状**：VMware/Hyper-V/WSL 适配器被枚举为第一个，APP 连不上。
**对策**：优先级排序 = 默认路由网卡 > 192.168.x > 10.x > 172.16-31.x，排除 `127.*`、`169.254.*`、虚拟网卡特征名；设置页展示**全部候选**让用户手选（这是兜底，也是最快排障入口）。

### 🟡 T-15 · PyInstaller 升级导致打包静默失败
**对策**：`requirements.txt` 锁 PyInstaller 版本；升级后必须重跑「打包 + 双击 + 打开登录页 + 一笔入库 + 备份」全流程（UT 无法覆盖，属手工门禁项，见 08-上线检查清单）。

### 🟡 T-16 · exe 放在 `Program Files` / 桌面受保护目录无法写库
**对策**：数据目录强制走 `%LOCALAPPDATA%\ScanableSelf\`；启动时做「目录可写自检」（写一个 `.probe` 文件），失败弹窗并说明，不要抛未捕获异常静默退出。

### 🟡 T-17 · 无控制台模式下异常看不见
**对策**：`sys.excepthook` + `threading.excepthook` 双钩子：写日志（CRITICAL）+ `ctypes.MessageBoxW` 弹窗（含 `trace_id`）；启动阶段任何异常都必须有用户可见反馈。**自用项目最大的敌人是「双击没反应」**。

### 🟡 T-18 · Flask `SECRET_KEY` 每次启动随机 → Session 全失效
**对策**：首次启动生成并**持久化到 `config.ini`**；轮换需明确告知会踢掉网页登录（Token 不受影响，因为存库哈希）。

### 🟢 T-19 · `SELECT *`
Repository 必须显式列字段。表加列后 `SELECT *` 会让 `zip()` 映射静默错位，且难复现。

### 🟢 T-20 · 枚举大小写混用
写库前统一 `.upper()`（`type`/`source`/`partner.type`/`sync_status`），角色 `admin`/`operator` 保持小写；`CHECK` 约束兜底 + 单测断言禁止小写 `in`。

### 🟢 T-21 · 数量/金额的浮点累加
`quantity` 全程 `int`；金额 `round(x, 2)` 只在写入与展示两处做，中间态用 `REAL` 不做二次 round（避免 0.005 漂移叠加）。

### 🔴 T-23 · 嵌套事务直接发 BEGIN
**症状**：单笔出入库一切正常；批量同步（外层已开事务）一进来就 `500`，日志里是
`sqlite3.OperationalError: cannot start a transaction within a transaction`。
**根因**：`database.transaction()` 无条件 `BEGIN IMMEDIATE`，而批量同步是「外层事务 + 每条内部再调一次事务」。
**对策**：事务原语必须可重入 —— `conn.in_transaction` 为真时改用 `SAVEPOINT`/`RELEASE`/`ROLLBACK TO`，
且内层失败只回滚内层，不得把外层已写的流水一起带走。已有回归测试守住（`test_nested_transaction_uses_savepoint_not_begin`）。

### 🟡 T-24 · 备份文件名的秒级粒度
**症状**：连续点两次〔立即备份〕或手动与自动同秒触发，`backups/` 里只剩一个文件，**前一份被静默覆盖**。
**根因**：文件名只到秒 + `open(...,'w')` 语义。备份被覆盖却没有任何报错，是自用系统最坏的一类静默失败。
**对策**：撞名自动追加序号（`_2`、`_3`…）；列表排序按解析出的时间戳而非文件名字典序。
回归测试：`test_backup_names_are_unique_and_timestamped`、`test_backup_list_orders_by_real_time_not_string_luck`。

### 🟢 T-22 · 页面里循环查库（N+1）
模板/视图禁止逐行发 SQL。列表页要关联名（如流水页的商品名）用 `JOIN` 或冗余快照字段一次取回。仪表盘 4 个聚合查询必须各自走索引（见 02 文档索引清单）。

### 🟡 T-25 · CSP `default-src 'self'` 禁内联脚本 → 深色模式闪白
**症状**：把主题初始化写成 `<script>...</script>` 后控制台报 CSP 违规、脚本不执行；若改成 `DOMContentLoaded` 里执行，则深色用户每次刷新都先看到浅色再跳变（闪白）。
**根因**：CSP 未放开 `script-src`，内联脚本一律被拒；而推迟到 body 末尾执行必然晚于首屏绘制。
**对策**：主题初始化必须是**同源独立文件、放在 `<head>` 内同步加载**（`static/js/theme.js`），在 `<body>` 解析前把 `data-theme` 写到 `<html>`。界面逻辑另放 body 末尾的 `shell.js`。

### 🟡 T-26 · 局域网 HTTP 下 `navigator.clipboard` 不存在
**症状**：内网用 IP 访问时「复制」按钮无声失败（`TypeError: Cannot read properties of undefined`）。
**根因**：本项目是明文 HTTP，**非安全上下文**，浏览器不暴露 `navigator.clipboard`。
**对策**：复制必须走 `window.isSecureContext` 判断 + `document.execCommand('copy')` 回退。此处回退不是老浏览器兼容，而是本项目的正常路径，**不可删除**。

### 🟡 T-27 · Jinja `groupby` 不排序 → 同一分组被拆成多段
**症状**：侧边导航里「系统管理」出现两次，或分组顺序随机。
**根因**：Jinja 的 `groupby` 直接映射 `itertools.groupby`，**只合并相邻元素**，不预先排序（与 SQL `GROUP BY` 语义不同）。
**对策**：由 Python 侧 `nav_links()` 按 `NAV_GROUPS` 顺序排好再交给模板；`|rejectattr(...)|groupby(...)` 会保持相对顺序，但**不得**在模板里对未排序序列直接 `groupby`。

### 🟢 T-28 · 复用 `sd-*` 类名前先确认语义一致
**症状**：把 `.sd-nav/.sd-nav-link`（顶栏）改造成侧栏导航样式后，`report/summary.html` 与 `master/partners.html` 的页内维度/类型切换器一起被改坏（竖排、错位）。
**根因**：这两个类被 3 处复用，语义是**横向分段控件（Segmented）**而非侧栏导航。
**对策**：侧栏另起 `.sd-sidenav-*`，`.sd-nav/.sd-nav-link` 保留为 Segmented 并单独立规；同理 `.sd-label` 是全站表单 `<label>` 的类名，标签打印区不得复用（40×30mm 虚线框会污染所有表单标签）。

### 🟡 T-29 · 深色模式的打印与扫码
**症状**：深色模式下 `Ctrl+P` 打出黑底白字、白纸黑墨全浪费；若让二维码/条码跟随主题变成浅色码，扫码器直接读不出来。
**对策**：`@media print` 里把 `--win11-*` 变量组强制复位为浅色（不依赖 JS，因为 `data-theme` 仍在 `<html>` 上）；`.sd-barcode` 与 `.sd-qr` 显式锁定 `background:#fff` + 深色码，不跟随主题。

### 🔴 T-30 · 改 `.py` 后不重启 → 内存旧模块 + 磁盘新模板的混合态
**症状**：改完 `views/__init__.py`（`nav_links()` 补 `group`/`icon`）后刷新页面，浏览器只看到 waitress 自己的 `Internal Server Error`（不是站内的「操作无法完成」页）；日志里只有 `未捕获异常 trace_id=...`，且 `exc` 全是 flask 框架帧，看不到异常类型。三个请求连续复现，重启后自愈。
**根因**：`runserver` 由 waitress 承载，**没有 werkzeug 重载器** —— `.py` 改动永不生效，而 Jinja 模板每次请求从磁盘重新编译。于是「新 `base.html` 按 `item.group` 分组渲染 + 内存里旧 `nav_links()` 只返回 `label`/`href`」→ 渲染期 `UndefinedError`；又因 `errors/500.html` **同样继承 `base.html`**，500 处理器自己再炸一次，异常逃出 Flask，最终由 waitress 兜底吐它自己的错误页。
> 推论：**看到 waitress 的错误页 = 站内 500 错误页也渲染失败了**。别去查 `errors/500.html` 的文案，去查出错页与它共享的祖先 `base.html`。
**对策**：① 改任何 `.py` 后必须重启进程（模板能热重载，这正是最易误判处：`Ctrl+F5` 后好一半说明是代码没重载，不是浏览器缓存）；② 排查先比时间：`Get-Process python* | Select StartTime` 对比 `Get-Item <改动文件> | Select LastWriteTime`；③ 别把 `core/logging_setup.py:EXC_LIMIT`（2000）压回 500 —— 500 字符正好截在 flask 框架帧上，等于没留堆栈。

### ⚪ T-31 · （已作废）皮肤改造把通用样式收窄成 class 选择器
**作废原因**：自研 Fluent 皮肤与全部 Jinja 模板已下线，界面改由 antd 5 + SPA 渲染（docs/09 U3），

### 🔴 T-32 · `pytest` 全绿、`runserver` 正常，但双击 exe 只剩一个弹窗
**症状**：`dist\ScanableSelf\ScanableSelf.exe` 双击无界面、无日志，或弹「启动失败：xxx」；`%LOCALAPPDATA%\ScanableSelf\logs\` 完全不生成 —— 说明失败发生在 `ensure_dirs()` 之前。**这时先怀疑打包，不要怀疑业务代码**。按暴露顺序：
1. **`pkg_resources` 运行期钩子**：依赖图里只要有 `pkg_resources`，PyInstaller 就挂 `pyi_rth_pkgres`；而 setuptools 的 `pkg_resources` 在较新解释器上 import 即抛异常 → 冻结后启动直接 `ImportError`。对策：`excludes=["pkg_resources", "setuptools"]`（顺带省约 7MB）。
2. **入口调用写在文件中部**：`app.py` 的 `if __name__ == "__main__": main()` 曾排在 `_setup_web_login` 定义之前 → `NameError`。开发态走 `manage.py` 导入模块（`__name__ != "__main__"`）永不触发，而 PyInstaller 偏偏以 `__main__` 执行 `app.py`。对策：入口**必须放文件最后一行**。
3. **动态导入的蓝图收集不到**：`api/__init__.py`、`views/__init__.py` 用 `import_module(f"{pkg}.{name}")` 循环注册，静态分析全看不见 → `No module named 'api.ping'`。对策：spec 里 `collect_submodules("api") + collect_submodules("views")`，并用 `sys.path.insert(0, SPECPATH)` 保证 collect 能 import 到本项目包。
4. **spec 里的假条目**：barcode 的 `upc/ean` 子目录在 0.15.1 里不存在（打包**期**直接失败）；不存在的 hiddenimport 只报 `ERROR: Hidden import ... not found`，噪音会掩盖真错误。对策：datas/hiddenimports 只写实际存在的项，barcode 路径用 `os.path.dirname(barcode.__file__)` 动态解析，禁止写死 `.venv` 路径。
5. **★PyInstaller 5.x 的产物结构与 6.x 完全不同**：6.x 把所有东西塞进 `dist\<名>\_internal\`，而 **5.13.2（Win7 线的最后版本）的 onedir 产物没有 `_internal`** —— DLL、`python3xx.dll`、`base_library.zip` 与 `datas` 全都直接落在 `dist\<名>\` 下。因此：
   - 凡按 6.x 写的排查手法（「看 `_internal` 里少了谁」）在 5.x 上**全部失效**，别照着找；
   - 判据改成看 `dist\ScanableSelf\` 根目录下是否齐了 `python3x.dll` / `base_library.zip` / `templates\` / `static\` / `db\`；
   - 双击了 `build\` 里的半成品 exe 依旧会报找不到 Python DLL，交付与验收**只认 `dist\ScanableSelf\ScanableSelf.exe`**。
6. **`datas` 少目录 = 界面上直接出事**：本项目至少要带 `templates`（错误页）、`static`（含 `static/spa` 构建产物）、`db`（schema 与 migrations）、`license/resources/keys/public.pem`。漏 `static/spa` 的表现见 T-36。
**排查手法**：`$p = Start-Process <exe> -PassThru -RedirectStandardError err.txt` —— GUI 子系统的 exe 只要拿到有效文件句柄，PyInstaller 就会把 traceback 写进该文件（双击时才变成弹窗）。
**本机环境另注**：IDE 的删除守卫会劫持 `shutil.rmtree`，PyInstaller 清理旧 `dist\` 时会崩在 `sitecustomize.py` → 打包前先手工删掉 `dist\ScanableSelf`，且 `--noconfirm` 不要配 `--clean`。

### 🔴 T-35 · SPA 通配回退把 `/api/*` 的 JSON 404 变成 HTML
**症状**：SPA 上线后，手机端（或前端自身）请求一个拼错的接口路径，拿到的是 `200 text/html`（一页前端壳），
于是「路径写错」被当成「服务端返回了奇怪的东西」，解析失败报的错离真正原因十万八千里。
**根因**：为了让前端路由可用，服务端必须有兜底路由（`views/spa.py` 的 `/<path:subpath>`）。
一旦写成「其它路由都匹配不到就回 index.html」的通配形式，`/api/xxx` 这种**没有路由的接口路径**
也会命中兜底 —— 接口 404 就此消失。
**对策**：
1. 兜底里显式排除 `/api`、`/healthz`、`/static` 等前缀，直接 `abort(404)` 交给 404 处理器（`/api` 前缀回 JSON 包络）；
2. **连带影响**：`request.url_rule` 从此对任何路径都非空，「有没有匹配到真实路由」不能再靠它判断。
   `app.py` 的强制改密门禁必须额外排除 SPA 兜底端点，否则「路径写错」会被判成 403/1004 ——
   而客户端收到 1004 的语义是「无权限/需重新配对」，又是一次误报。
3. 用例守门：`tests/test_spa_serving.py::test_api_404_stays_json_not_html`。

### 🔴 T-36 · 前端构建产物没随包 → 打开就是白屏
**症状**：服务端日志一切正常、`/api/ping` 也通，但浏览器打开只有一片白（或浏览器控制台报 404 找不到 `/assets/index-xxx.js`）。
**根因**：界面已改由 `desktop/web` 构建到 `desktop/static/spa/` 的静态产物渲染。
构建产物**不随包提交 / 没进 PyInstaller `datas`** 时，服务端拿不到 `index.html`。
**对策**：
1. 约定「**改前端必须 `npm run build` 后一起提交**」（产物入库，见 docs/09 S4）；
2. `views/spa.py` 在 `index.html` 不存在时返回一页**人话提示**（写清是在 `desktop/web` 跑 `npm run build`，
   还是打包漏了 `datas`），绝不返回 500 或空白 —— 现场没人能看着白屏猜原因；
3. 用例守门：`test_missing_build_gives_actionable_page`；`test_smoke.py` 另有一条断言构建产物路径存在。

### 🟡 T-37 · antd v5 在旧内核浏览器上样式失效
**症状**：界面能跑但「没样式」—— 控件是裸的、间距全乱、弹层位置错位；控制台不见报错。
**根因**：antd v5 的 CSS-in-JS 依赖 `:where()` 选择器（Chrome 88+）。若现场用的是
360 安全/极速浏览器、QQ 浏览器等**内核停在 63~87** 的壳浏览器，` :where()` 不生效，样式整片失效。
**对策**：
1. Vite `build.target` 锁 `chrome88`，保证**产物语法**不新鲜于基线；
2. 上线前**实测现场浏览器的内核版本**（`chrome://version` 或 JS 里读 UA），不要只看「是 Chrome 图标」；
3. 若内核确实过旧：按 antd 官方 `StyleProvider` + `hashPriority="high"` 降级方案处理，
   或统一改用 Chrome/Edge 109 便携版（Win7 上可用的最高版本）。
**不适用**：本项目不针对 IE。

### 🟡 T-38 · Win7 上 Python 与依赖的版本线（写错一个就装不上）
**症状**：Win7 SP1 上安装 Python 3.9+ 的安装器直接拒绝运行，或装完 `import` 就报缺 DLL。
**根因与对策**：
1. **Python 3.8.10 是最后支持 Win7 SP1 的官方版本**（3.9+ 的安装器要求 KB2533623 等补丁），运行时线锁死 3.8.10；
2. **PyInstaller 5.13.2 是最后支持 Win7 的版本**（6.x 已放弃），且其产物结构见 T-32 第 5 条；
3. 依赖必须逐个核对 Win7 可用性：`waitress` 3.0.0 要求 Python ≥3.9 → 停 2.1.2；
   `Pillow` 10.x / `cryptography` 43.x 的 wheel 对 Win7 的支持未在真机验证过 → 分别停 9.5.0 / 41.0.7；
   纯 Python 的 `qrcode`/`python-barcode`/`python-dotenv` 无此风险；
4. **代码也要守 3.8 的语法线**：模块里用了 PEP 585（`dict[int, int]`）或 PEP 604（`int | None`）注解、
   又没写 `from __future__ import annotations` 的，**在 3.8 上导入期就会 `TypeError`**。
   核心里被 `app.py` 早期导入的模块（`core/errors.py`、`license/*`）栽一次就是整个程序起不来。
5. **本机（Python 3.12 + Win10）的结论不能外推**：本节所有条目都是**真机验收项**，
   清单见 `docs/12-Win7服务端部署与Python3.8验收.md`。

| 项 | 规定 |
|---|---|
| Python | 3.11；`snake_case` 模块/函数、`PascalCase` 类、常量 `UPPER_SNAKE`；行宽 100；4 空格 |
| 类型注解 | 所有函数签名必须有注解；Repository 返回 `dict` 或 `list[dict]`，不用自定义 Row 类 |
| 注释 | **中文**；模块头注释写明「职责 + 所属 PRD 章节 + 相关陷阱编号」；魔法逻辑必须有注释 |
| 分层 | `api/`（HTTP 层，只做参数解析+校验+调 service+包响应）→ `services/`（业务规则+事务）→ `models/`（SQL+行转换）。**禁止**跨层：`api` 不写 SQL，`models` 不判业务 |
| 错误处理 | 业务错误抛 `BizError(code, msg, data, http_status)`；`api` 层全局 `errorhandler` 转包络。禁止 `except: pass`、禁止裸 `except Exception` 后返回 200 |
| 响应构造 | 一律用 `core/response.py:ok()/fail()`，禁止手写 `jsonify` 字典（保证 `trace_id` 与包络一致） |
| 前端 | 原生 HTML/CSS/JS + 自研 Win 风格皮肤（无 UI 框架、无构建）；`static/js/` 按页拆分，全局只 1 个 `common.js` |
| Git | 分支 `main` + `feat/*`；提交 `<type>: <中文描述>`，type ∈ {feat,fix,docs,test,chore,refactor}；一个提交一个可验证意图 |
| 命名一致性 | 库存方向词全局唯一：入库 `IN`、出库 `OUT`、调整 `ADJUST`；禁用 `STOCK_IN`/`IMPORT`/`io_type` 等变体 |

## D2. 测试与工具链的两个非代码坑（本项目实测）

1. **凭据字面量会被写盘安全策略改写**：源码里出现 `password="某个真实串"` 这种形态时，
   写入环节会把值替换成 `***`，导致磁盘上的测试文件与实现**静默不一致**（表现为「哈希永远校验失败」，
   极难定位）。约定：测试口令一律用运行时拼接常量（`"Adm1" + "n-Test"`）+ 表单助手构造，
   源码中不留「凭据键 + 字面量」形态。本项目两次踩到（`tests/factories.py`、登录用例）。
2. **进程级全局状态必须每测试复位**：登录失败计数（`services/login_guard.py`）是模块级字典，
   不复位会让「锁定用例」污染后续所有登录测试。`tests/conftest.py` 已加 autouse 复位夹具。
